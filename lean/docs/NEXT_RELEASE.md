# After v0.6: next performance work

Keep v0.6 on its Code-OSS 1.139.1 base while finishing the release. On 28 September 2026, upstream `release/1.139` still points to our base commit (`04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1`). Upstream `main` is a much larger version migration, not a safe v0.6.1 patch. Review its security and correctness changes separately, establish ancestry in the partial clone, and take a newer base only as a planned compatibility release with extension, update, and performance checks.

The next minor version should begin with measurements, then ship only a change that wins a matched signed-app comparison without breaking editing or review:

1. **Profile extension-host readiness on a real installed extension.** The Finder path is now faster, but the signed release still needs an extension-backed editable file above one second at p95. Trace shell resolution, extension scan, activation, and the first edit probe with an established profile. Audit whether upstream's newer generated code-cache work can be adapted to this base; the Electron custom-protocol cache is already enabled, so do not assume that switch is missing. Keep extension APIs and startup activation intact.
2. **Measure the GPU footprint across independent launches.** A single v0.6 GPU sample was large and highly variable. Record process roles, window size, displays, and idle/active states for repeated Lean and original Code-OSS launches before touching GPU settings. Test rendering, scrolling, diff editors, and webviews before accepting any reduction. Never trade visual correctness or security for an idle-only number.
3. **Trace terminal-host startup before deferring it.** If a no-terminal window starts the pty host on the editor critical path, try starting it on first terminal use. Preserve terminal restoration, reconnection, tasks, extension terminals, and the first command. Measure both launch-to-edit and first-terminal latency; do not improve one by silently delaying the other.

Next, audit the remaining main/shared-process AI wiring and packaged Agents resources for a narrow removal that preserves MCP and language-model extension APIs. Test a larger truly optional renderer graph only if CPU profiles show material startup evaluation time. A second-window and painted Git-diff benchmark would better represent the review workflow than a blank-window timestamp. The [optimization ledger](OPTIMIZATION_LEDGER.md) records earlier rejected prototypes and the [performance history](PERFORMANCE.md) defines the Code-OSS comparison and benchmark cadence.
