# Next release: v0.8 startup candidate

The signed public release is v0.7.0. The v0.8 source branch currently has three retained cold-renderer cuts: the [optional Quick Chat split](V0.8_COLD_RENDERER_SPLIT_DESIGN.md), the [terminal chat-context helper isolation](../performance/v0.8.0-terminal-context-cut.json), and the [chat-pet renderer boundary](../performance/v0.8.0-chat-pet-renderer-cut.json). The current desktop initial static graph is 31,552,220 unminified JavaScript bytes. This is **bundle evidence**, not a startup-time, disk, or memory gain. The [ledger](OPTIMIZATION_LEDGER.md) also records rejected cuts, including a language-model image-helper lazy import that made the graph larger and a chat-session status extraction that broke required service registration.

Keep small, plausible cuts only when emitted graph output improves and focused correctness checks pass. The owner has deferred further GUI timing until requesting one combined test of the accumulated changes. Do not add isolated speed percentages or sum byte cuts as latency savings. The final public comparison, when requested, must use signed Lean against original same-revision Code-OSS in the same build mode; direct Lean-version diagnostics stay internal.

Before a v0.8 release, build the production-minified candidate and verify editing/save, file and text search, terminal, local Git diff, installed extension activation and webview. Exercise first-use Quick Chat, chat-pet creation and host switching, and terminal attach-to-chat because those paths changed. Then complete signing, notarization, archive identity, installed-app, and applicable updater checks. Update the changelog, README, website, and release notes with version-labeled facts; keep older speed and memory figures attributed to the releases that measured them. The sub-one-second p95 target remains unproven.

## Earlier v0.6 and v0.7 leads

At v0.6, the project kept its Code-OSS 1.139.1 base. On 28 September 2026, upstream `release/1.139` still pointed to our base commit (`04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1`). Upstream `main` was a much larger version migration, not a safe patch. A future upstream-base change needs a planned compatibility release with extension, update, and performance checks.

The v0.6 review proposed these leads; the v0.8 plan above and the owner's later benchmark cadence supersede its measurement timing:

1. **Profile extension-host readiness on a real installed extension.** The Finder path is now faster, but the signed release still needs an extension-backed editable file above one second at p95. Trace shell resolution, extension scan, activation, and the first edit probe with an established profile. The newer upstream packaged Node compile cache is not a macOS candidate now: [upstream disabled its generation and use on POSIX](https://github.com/microsoft/vscode/commit/157fc59ed6cc6bd7fe1be30bd2e74200a2f9bfca) after portable-cache validation failed. Retain the existing writable per-user cache; only test a small early-main-process extension of it if a current trace attributes material time there. Keep extension APIs and startup activation intact.
2. **Measure the GPU footprint across independent launches.** In one v0.6 candidate launch, Lean's GPU role jumped from about 124 MB to 525 MB across three snapshots; Code-OSS also had a large transient reading. This does not establish a persistent or Lean-specific cost. Record process roles, window size, displays, and idle/active states for repeated Lean and original Code-OSS launches before touching GPU settings. Test rendering, scrolling, diff editors, and webviews before accepting any reduction. Never trade visual correctness or security for an idle-only number.
3. **Keep terminal deferral low priority.** Source review shows the pty host is already launched on demand and a previous startup trace recorded 0 ms at millisecond resolution for local backend registration. Early registration is required when a remote resolver opens a local terminal. Revisit only if a repeatable no-terminal trace identifies material remaining work; preserve terminal restoration, reconnection, tasks, remote connections, extension terminals, and first-command latency.

Next, audit the remaining main/shared-process AI wiring and agent-host resources for a narrow removal that preserves MCP and language-model extension APIs. Test a larger truly optional renderer graph only if CPU profiles show material startup evaluation time. A second-window and painted Git-diff benchmark would better represent the review workflow than a blank-window timestamp. The [optimization ledger](OPTIMIZATION_LEDGER.md) records earlier rejected prototypes and the [performance history](PERFORMANCE.md) defines the Code-OSS comparison and benchmark cadence.

The v0.7 branch retained omission of the unused desktop Agents-window bundle, removing about 20.5 MiB of packaged resources without a startup claim. The main-process Node cache candidate was removed after paired GUI trials found no reliable tail-latency improvement. Nine independent, compact-window candidate memory pairs against original Code-OSS measured 573 versus 706 MiB median app-tree footprint after 30 seconds idle; the GPU role was bimodal in both apps, so there is no evidence for a Lean-specific persistent 515 MB GPU cost. An architecture review found no third small, safe speed change supported by the old v0.5 trace: storage and workspace initialization already overlap, and moving them earlier risks profile and trust state. Require at least 100 ms of reproducible critical-path work before another scheduling change.

The Startup Performance view's `cached data: YES/NO` field is only a heuristic: it compares the current commit with `perf/lastRunningCommit` in application storage, and does not read a Chromium cache-hit counter. A fresh isolated profile therefore reports `NO` even when the runtime cache is configured. Check the profile condition, cache directory and affected timing spans before treating that label as evidence of a cache problem.
