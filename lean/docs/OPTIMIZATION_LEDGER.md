# Optimization ledger

This is the running record of Lean VS Code performance work. It separates **shipped behavior**, **development experiments**, and **untried ideas**. Public release speed claims use signed Lean builds against original Code-OSS built from the [same upstream revision](PERFORMANCE.md) and in the same build mode; unsigned candidate diagnostics are labeled as such. A direct Lean-version comparison helps diagnose a change but is not a public Code-OSS gain. The current signed release is v0.7.0. Its direct packaged-app comparison shows 64.9% less apparent content than original same-revision minified Code-OSS. The last signed paired speed result belongs to v0.6.0; v0.7.0 makes no new public startup or memory percentage claim.

The main target is a requested file that accepts an extension-backed edit from a stopped Apple Silicon app at **p95 below one second**. The v0.6.0 unsigned-candidate extension-backed run measured **1,427 ms p95**; the signed-release counterpart was interrupted on request, so the target remains open. Synthetic UI input, visible DOM text, a second window, and a saved edit are useful *separate* endpoints; none substitutes for that target.

The detailed trial notes and links are in the [startup roadmap](STARTUP_ROADMAP.md). Exact signed-release comparisons, raw reports, profile conditions, and known regressions are in [performance history](PERFORMANCE.md). Do not promote a development trial, small exploratory sample, unminified comparator, or one-launch memory snapshot into a public release claim.

The [v0.8 startup investigation](V0.8_STARTUP_INVESTIGATION.md) corrects two tempting trace readings: the 707 ms “extensions registered” figure is cumulative startup time rather than extension-scan cost, and moving shell collection earlier after configuration and primary-instance ownership offers at most about 14 ms in the available candidate trace. Its workbench module preload was rejected after a focused A/B trace and one extension-editable-file pair found no directional benefit. A later [single-launch shell-gate diagnostic](../performance/v0.8.0-shell-gate-focused-diagnostic.json) saw 107 ms of renderer shell-promise wait after host allocation; this is a possible overlap lead only. Startup Performance snapshots main marks at window creation, so delaying its display cannot recover the missing main-process shell-completion mark. Package validity or a single trace is not a startup result.

A [fresh-versus-warmed V8 diagnostic](../performance/v0.8.0-renderer-v8-cache-focused-diagnostic.json) found 435.583 ms of background parsing for the workbench module inside a 564 ms fresh-profile import. After one warm-up, Chromium consumed an 11.7 MB valid module code cache and the import took 113 ms in that separate launch. The faster warmed renderer reached extension-host allocation while the shell promise still had 270 ms to run; the cold launch's shell promise had already resolved before allocation. This confirms a substantial **cold** parse cost and identifies a separate **warmed** shell gate; it does not prove a reliable startup gain or predict established-profile file readiness. Astra's architecture review rejected spawning the host before the final shell environment exists, because Node/Electron and the bootstrap read that environment at process start. The Startup Performance `cached data: NO` label is a heuristic and did not reflect the cache actually consumed in the Chromium trace. A later [exact main shell trace](../performance/v0.8.0-main-shell-gate-focused-diagnostic.json) measured 741 ms of shell resolution in one established-profile launch, with the host wrapper allocated 119 ms before completion. A separate three-run no-op zsh probe took 660–765 ms, suggesting this Mac's shell initialization dominates the interval; neither single-app observation is a recoverable saving or a Code-OSS comparison.

Lower-priority, untried ideas remain in the [startup roadmap](STARTUP_ROADMAP.md): defer optional workbench-contribution construction only if profiling puts it on the critical path; defer optional shared-process channels only if a real file-ready wait is attributable to them; and verify whether the pinned Electron distribution already includes its native startup optimizations before testing custom snapshots. An always-resident background process could accelerate a later open but would increase idle resource use and would not count toward the stopped-process goal. None has a measured gain.

The [developer workflow benchmark matrix](BENCHMARK_MATRIX.md) defines the next public-use endpoints: a **painted local Git diff**, **Quick Open to an editable file**, and an **installed language extension's first diagnostic** are the highest-value missing checks. Also test Search-panel results, a real multi-root project, a large file, webview content readiness, and the first window's responsiveness after a second window opens. Record action-only latency beside launch-to-completed-task latency, including regressions; do not select workloads just because their percentage is large. Public speed claims require at least 30 alternating pairs against original same-revision Code-OSS, equal fixtures and build modes, and retained failed samples.

## Release closure

For each release, update this ledger's statuses and the [changelog](../../CHANGELOG.md); verify editing/save, Git diff, search, terminal, installed extension, webview, restored editor, and first use of any deferred feature affected by the changes. Build and verify the signed/notarized DMG and update ZIP, install on the reference Mac, and complete an applicable native update trial. Run the primary 30-pair GUI comparison and selected workflows against original same-revision Code-OSS only for a major release or when the owner explicitly requests it, retaining raw results in `lean/performance/`. Minor and patch releases use focused checks and keep older speed and memory claims explicitly version-labeled. A direct packaged-bundle size comparison may be recorded separately. Update the README and public website only with measured Code-OSS gains and caveats.

The final achievement summary should give the shipped changes and benefits, the primary median and p95 against Code-OSS, the established-profile result, other completed workflows and any slower actions, independent-launch memory evidence or its absence, all rejected trials and reasons, and the remaining experiments ranked by evidence and affected use case. State explicitly whether the sub-one-second p95 target was met. Historical Lean-version results stay available here and in performance history, while the website continues to compare only against original Code-OSS.
