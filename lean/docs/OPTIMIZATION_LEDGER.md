# Optimization ledger

This is the running record of Lean VS Code performance work. It separates **shipped behavior**, **development experiments**, and **untried ideas**. The public comparison is always the signed Lean release against original Code-OSS built from the [same upstream revision](PERFORMANCE.md) and in the same build mode. A direct Lean-version comparison helps diagnose a change but is not a public Code-OSS gain. The current signed release is v0.5.0. Its full paired benchmark uses original same-revision minified Code-OSS.

The main target is a requested file that accepts an extension-backed edit from a stopped Apple Silicon app at **p95 below one second**. The signed v0.5.0 matched-build run measured **2,009 ms p95**, so this target remains open. Synthetic UI input, visible DOM text, a second window, and a saved edit are useful *separate* endpoints; none substitutes for that target.

## Changes and experiments

| Change or experiment | Status and observed result | What it means |
| --- | --- | --- |
| Curated 33 bundled extensions; default telemetry, experiments, recommendations, onboarding, and built-in AI surfaces disabled | Shipped in v0.2.0. The signed release measured 18% less median editable-file time than same-revision Code-OSS in its own paired run. | The full-fork result cannot be assigned to any one removed default. Editing, Git, terminal, and optional extensions remain available. |
| Remove generated JavaScript source maps from the app copy | Shipped in v0.2.0; about 227 MiB less uncompressed package data. | Disk-size saving only; no measured runtime-memory or startup saving is attributed to it. |
| Activate bundled Git on demand | Shipped in v0.3.0. A direct candidate-versus-v0.2.0 repository trial showed no file-ready improvement (1,662 vs 1,652 ms median). | Retains Git review while avoiding default activation; no startup percentage is attributed to this individual change. The first Git action in the v0.4.0 Code-OSS trial was slower in Lean. |
| Production-minified macOS bundle, removal of eager remote-listener lookup, and early single-flight shared-utility initialization after the first real window | Shipped together in v0.4.0. Signed v0.4.0 was 5% faster at median than signed v0.3.2 in a direct paired run. In a separate matched-build-mode run it was 17% faster at median than same-revision Code-OSS. | These are whole-app results under different comparisons; the three changes do not have isolated public gains. [Release notes](RELEASE_NOTES_0.4.0.md) record signing, updater, and feature checks. |
| Curated release app-bundle footprint | The signed v0.4.0 app contains 537.8 MiB apparent file content versus 1,462.9 MiB in the same-revision locally built Code-OSS package: 63.2% less. The signed Lean DMG is 206.8 MB. | [Bundle-size report](../performance/v0.4.0-bundle-size-vs-code-oss-1.139.1-minified.json) includes the method. Fewer built-in extensions and generated assets contribute; no individual change gets the whole percentage. The DMG has no matched baseline image, and neither number proves a runtime-memory reduction. |
| v0.5.0 installed app-bundle footprint | The signed v0.5.0 app has 537.7 MiB apparent content versus 1,462.9 MiB for matched original Code-OSS: 63.2% less. Its DMG is 211.3 MB. | [v0.5.0 report](../performance/v0.5.0-bundle-size-vs-code-oss-1.139.1-minified.json). A matched Code-OSS DMG was not measured. This is disk content, not a v0.5.0 runtime-memory claim. |
| Short-idle app-tree footprint | In nine independent fresh-profile launch pairs, signed v0.4.0 used 655.3 MiB median after 30 seconds idle versus 786.5 MiB for same-revision minified Code-OSS: 16.7% less. Lean was lower in all nine pairs. | [Raw paired report](../performance/v0.4.0-independent-memory-vs-code-oss-1.139.1-minified.json). The method sums per-process macOS physical footprints in an isolated 100 KiB-file workload. It does not establish peak, long-session, or extension-heavy memory use, nor a memory gain over v0.3.2. |
| Bundled-extension manifest index and earlier extension scan | Prototyped before v0.4.0; not retained after the editable-file trial showed no gain. | Do not repeat without evidence that scanning has moved onto the critical path. |
| Start local extension initialization at workbench Ready instead of an extra idle callback | Shipped in signed v0.5.0. The 30-pair release run reached an editable file in 1,653 / 2,009 ms median / p95 versus 1,960 / 2,254 ms for original minified Code-OSS. | The 16% median difference is a whole-fork result, not the isolated gain from this callback change. Editing, search, terminal, Git, webview, and Open VSX installation passed release checks. |
| Start extension initialization in the service constructor | Prototyped and reverted after the editable-file warm-up failed to finish within 120 seconds. | Too early for the service's lifecycle; preserve the workbench-Ready boundary unless dependencies change. |
| Fork the extension host while the renderer requests its shell environment | Prototyped and reverted. The prepared host led actual demand by only 7–40 ms in three exploratory launches. | Process lifecycle and option-matching complexity exceeded the available overlap. |
| macOS-only renderer specialization | Prototyped and reverted; it changed the minified bundle by only 83 bytes. | No plausible material startup saving at that boundary. |
| Split an optional AI Customizations editor pane from the initial renderer bundle | Prototyped and reverted. The first split emitted no lazy chunks; the revised split emitted only a 427 KiB genuinely lazy editor chunk and a 3.78 MiB eager shared chunk. A five-pair unsigned-candidate diagnostic showed 1,232 vs 1,226 ms median against signed v0.4.0. | No observed file-ready gain. Any later split needs a larger truly deferred runtime graph and must preserve CSS, localization, editor restoration, commands, and first-use latency. |

The detailed trial notes and links are in the [startup roadmap](STARTUP_ROADMAP.md). Exact signed-release comparisons, raw reports, profile conditions, and known regressions are in [performance history](PERFORMANCE.md). Do not promote a development trial, small exploratory sample, unminified comparator, or one-launch memory snapshot into a public release claim.

## Next experiments and the use cases they could help

| Candidate | Admission test before implementation | Use cases and regression gate |
| --- | --- | --- |
| Defer a **substantial** optional renderer runtime graph, beyond one editor pane | A renderer CPU profile must attribute at least 150 ms of the editable-file path to separable optional module evaluation or compilation. Compare emitted **initial** and eager shared chunks, not only the entry file. | May help plain-file launch and Git review if optional chat/notebook/debug code is actually off their path. Measure first use of those features, restored custom editors, CSS, localization, commands, and extension APIs. |
| Pipeline final-window startup and essential configuration/storage reads with renderer loading | Trace at least 100 ms of independent work that can overlap without stale state, a replacement renderer, or main-process database work already being counted. | May help stopped-process file opening, project restore, and second-project-window readiness. Check single-instance handling, trust, file associations, restored state, multi-window operation, signing, and updater behavior. |
| Reduce optional extension API/RPC actor bootstrap | Profile the actual extension-host critical path and identify at least 100–150 ms of optional work; the renderer's extension-registration mark alone is insufficient. | May help extension-backed editable-file readiness and first language result. Preserve first incoming RPC, events, activation, documents, commands, terminal, debug, notebook, webview, and SCM compatibility. |
| Test workbench resource layout or precompiled hot resources | First show material file metadata/read, parsing, or compilation time on the critical path; verify Electron's existing optimizations before assuming a cache miss. | May help stopped-process and cold-cache file opening. Compare signed/notarized package, update ZIP, source maps, native modules, and first-use extension loading. |
| Measure peak and long-session memory under development workloads | The nine-pair short-idle trial above is complete; repeat with peak footprint and documented editor/review/search/terminal activity over longer sessions. | Tests whether memory remains lower after extensions and real work, or is merely shifted past the initial idle window. |

Lower-priority, untried ideas remain in the [startup roadmap](STARTUP_ROADMAP.md): defer optional workbench-contribution construction only if profiling puts it on the critical path; defer optional shared-process channels only if a real file-ready wait is attributable to them; and verify whether the pinned Electron distribution already includes its native startup optimizations before testing custom snapshots. An always-resident background process could accelerate a later open but would increase idle resource use and would not count toward the stopped-process goal. None has a measured gain.

The [developer workflow benchmark matrix](BENCHMARK_MATRIX.md) defines the next public-use endpoints: a **painted local Git diff**, **Quick Open to an editable file**, and an **installed language extension's first diagnostic** are the highest-value missing checks. Also test Search-panel results, a real multi-root project, a large file, webview content readiness, and the first window's responsiveness after a second window opens. Record action-only latency beside launch-to-completed-task latency, including regressions; do not select workloads just because their percentage is large. Public speed claims require at least 30 alternating pairs against original same-revision Code-OSS, equal fixtures and build modes, and retained failed samples.

## Release closure

For each future minor release, update this ledger's statuses and the [changelog](../../CHANGELOG.md); run the primary 30-pair GUI comparison and selected completed-workflow comparisons against original same-revision Code-OSS; retain raw results in `lean/performance/`; verify editing/save, Git diff, search, terminal, installed extension, webview, restored editor, and first use of any deferred feature. Build and verify the signed/notarized DMG and update ZIP, install on the reference Mac, and complete a native update trial. Then update the README and public website with only the measured release's Code-OSS gains and caveats.

The final achievement summary should give the shipped changes and benefits, the primary median and p95 against Code-OSS, the established-profile result, other completed workflows and any slower actions, independent-launch memory evidence or its absence, all rejected trials and reasons, and the remaining experiments ranked by evidence and affected use case. State explicitly whether the sub-one-second p95 target was met. Historical Lean-version results stay available here and in performance history, while the website continues to compare only against original Code-OSS.
