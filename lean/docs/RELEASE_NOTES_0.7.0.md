# Lean VS Code v0.7.0 release notes — draft

This is a release candidate record, not a published release or a performance claim. Keep the release unpublished until the signed app, updater, extensions, and editing/review workflows pass the checks below. Compare any new public speed or memory percentage with original Code-OSS from the fork's base revision `04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1`, built in the same minified mode.

## Candidate changes

- Retain the v0.6 Node compile cache for extension host, shared process, and terminal host. A main-process cache experiment was removed from v0.7 after exploratory paired trials showed no reliable tail-latency improvement.
- For macOS zsh, bash, and sh, use the system `env -0` command to read the login-shell environment without launching another Electron process to serialize it. The same login and interactive shell flags, cancellation, timeout, and environment cleanup remain; other shells keep the original collector. Focused parser and real-shell tests pass. A direct old/new login-shell comparison found the same 80 environment keys and identical `PATH`, `HOME`, and `SHELL`; zsh's optimized final command changes `SHLVL` and `_`, so the native path normalizes those to legacy values. A non-GUI subprocess probe suggests about 59 ms collector overhead can be removed, but the final app-level startup impact is still under test.
- Omit the separate Agents-window resources from the desktop package. The installed v0.6 app contained 21,542,445 bytes in `out/vs/sessions`; the current minified candidate contains no such directory. An Agents-window request opens a regular editor window, and an older Agents workspace opens as an ordinary workspace. This is package-content evidence, not yet a final signed-app size or startup-memory result.
- Make the startup trace warm-up quit through the editor. A signal-killed warm-up could leave Node's compile cache unwritten, so the trace now fails if the warm-up cannot quit normally. The benchmark also supports focused extension-backed startup trials and independent paired memory launches.

## Evidence and release gates

- Static checks: the desktop minified build at `b831827e34f6b8d1fec8143d15b7337b997575c9` completed with 22 bundles and the expected product commit; `out/vs/sessions` is absent. Typecheck, changed TypeScript lint, `lean:check-ai`, and the benchmark's fake-bundle smoke passed earlier in this branch. `node --check` and the fake-bundle smoke passed after the trace change. Repository ESLint still rejects the existing Lean `.mjs` scripts under its JavaScript-file policy; that is not a new runtime failure.
- **Candidate GUI checks:** a locally Developer ID-signed candidate at `cae9e6c00b7dfdd8ee14697f12eafac8b64e4269` passed edit/save verified on disk, 401-file project search and text matches, integrated-terminal command, local Git diff, and extension webview in the same 560 × 360 bottom-left window used for performance trials. The candidate has no timestamp or notarization and is not an installable public release. Normal Open VSX extension activation, Agents-window fallback, and restored legacy workspace remain to check on the final signed app.
- **Performance evidence:** the main-process cache experiment wrote about 3.4 MiB and a trace measured `import(main.js)` at 120 ms. A nine-pair candidate-versus-v0.6 trial found 1,362 vs 1,387 ms median editable-file time, but worse candidate p95 (1,623 vs 1,505 ms). A 30-pair compact-window trial also had worse candidate p95 through pair 24, then both apps slowed sharply under host load. We removed the cache and make no v0.7 startup claim from those runs. A [nine-pair short-idle candidate trial](../performance/v0.7.0-candidate-compact-memory-vs-code-oss-1.139.1-minified.json) against original minified Code-OSS measured 573 vs 706 MiB median app-tree footprint (18.8% lower by difference of medians) after 30 seconds with fresh profiles and identical small windows. Lean was lower in seven of nine pairs. Both GPU processes showed bimodal footprints, without a repeatable Lean-specific 515 MB idle cost. These candidate measurements are exploratory; final signed-build validation remains pending.
- **Current shell candidate startup diagnostic:** in [nine alternating compact-window established-profile pairs](../performance/v0.7.0-shell-candidate-vs-v0.6.0-compact-startup-diagnostic.json), the locally signed candidate reached an extension-editable file in 1,396 ms median / 1,528 ms p95 versus 1,484 / 2,654 ms for installed v0.6. The candidate was faster in all nine pairs, including a v0.6 outlier; the comparison includes the Agents-bundle omission and does not isolate the shell change. It is not a public Code-OSS speed claim.
- **Pending production release:** choose only measured, regression-safe changes; update the changelog and README; build the final source commit; sign and notarize the app, staple the app and DMG, and verify the update ZIP against the same app; run GUI feature and extension checks on that exact signed app; verify a v0.6 → v0.7 update; publish the GitHub release and live feed; install and verify the app; then update the website with concise, version-labeled claims and raw-method links.

The sub-second p95 extension-backed editable-file target remains open until a signed build demonstrates it. Earlier v0.6 figures remain labeled as v0.6 in the [performance history](PERFORMANCE.md); they do not automatically apply to v0.7.
