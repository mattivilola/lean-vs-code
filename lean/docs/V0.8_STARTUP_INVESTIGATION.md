# v0.8 startup investigation

This is a development record, not a v0.8 release commitment or a measured speed claim. The signed v0.7.0 app remains the current release. The next target is a stopped-process file that accepts an extension-backed edit at p95 below one second, with editing, Git review, terminal, installed extensions, signing, and updating intact. Record small candidate improvements independently and retain their code and method evidence. After the three-pair diagnostic below, hold further GUI timing until the owner asks for a combined trial of the accumulated changes. Typecheck, static guards, unit tests, and focused functional checks remain appropriate while implementing them. A combined effect may be smaller or larger than the sum of isolated effects; public speed claims still require a matched original Code-OSS comparison under the release policy.

## What the existing trace actually shows

The [sanitized admission record](../performance/v0.8.0-critical-path-admission.json) comes from an exploratory v0.7 trace with the subsequently removed main-process compile cache; it is useful for identifying work, not a signed-v0.7 timing baseline. It reports 120 ms to import `main.js`, 196 ms from `window.loadUrl()` to the renderer's workbench import, and another 120 ms to import the workbench. About 190 ms of the first renderer interval precedes workbench bootstrap execution. Blocking workbench contributions took 11 ms. “Extensions registered: 707 ms” is cumulative startup-to-registration time; the actual `register extensions & spawn extension host` span was 63 ms.

The shell collector starts at trace time 253 ms. Main services were created at 228–239 ms, initialized at 239–251 ms, and the primary-instance claim finished at 252 ms. Starting the same collector earlier after configuration and instance ownership offers only about 1–14 ms of overlap, so that proposal is rejected. The trace captured `willResolveShellEnv` but not shell completion; it does not establish the final v0.7 shell path's full critical-path cost. A previous extension-host prewarm prototype gained only 7–40 ms of lead and was removed.

Three retained, local v0.6 exploratory fresh-profile reports (product commit `0c349fe10c683500fb813278453f209b6f31d69b`) recorded workbench import spans of 719, 469, and 383 ms, each marked `cached data: NO`. Their window-load-to-import spans were 175, 230, and 168 ms. These old, single-app reports are not a v0.8 baseline or a paired speed result. They motivated checking an uncached fresh profile; the v0.8 preload did not show a directional file-ready benefit there, so an established-profile trial was not justified under the requested minimal test scope. The raw reports contain local paths and remain unpublished.

An Astra review of the new fresh-profile control report corrected further timing interpretations. The 280 ms `import(main.js)` figure begins at Node's process time origin and includes runtime startup; it does not attribute 280 ms to optional app code. The later `run main.js` span is 37 ms, though that does not cap parsing within the earlier interval. Storage initialization (213 ms) and workspace initialization (232 ms) begin together in a `Promise.all`, so their union is 232 ms rather than 445 ms. The 1,394 ms “extensions registered” value is cumulative; local extension-host readiness is roughly 2,151 ms from main time origin. The 465 ms from host allocation to process time origin includes a wrapper awaiting actual spawn, not 465 ms of process startup. A 113 ms host NLS-to-renderer-connection interval is a conditional profiling lead, not proven movable work. The report still lacks `code/didResolveShellEnv`.

The current local-host path awaits the shell environment before constructing the process options. `utilityProcess.fork()` snapshots the environment at spawn, and `bootstrap-fork` reads `VSCODE_ESM_ENTRYPOINT`, code-cache path, logging, error-handling, and parent-lifecycle variables before importing the extension host. Sending environment values after spawn cannot be assumed equivalent; the two-phase proposal needs a separately audited, environment-independent bootstrap before any implementation.

One further compact, fresh-profile launch of the unsigned no-preload control measured 161 ms from the renderer's `willStartExtensionHostProcess` to `didResolveExtensionHostShellEnv`; host allocation completed 107 ms before the shell-environment promise resolved. The extension-host `fork/start` mark followed 86 ms later, and the installed control extension activated normally. This is [single-launch diagnostic evidence](../performance/v0.8.0-shell-gate-focused-diagnostic.json) of a possible overlap, not a speed estimate or proof that 107 ms can safely move. The renderer mark includes IPC promise resolution and is not the precise main-process shell-completion instant. Delaying `perfview.show` by two seconds did not reveal `code/didResolveShellEnv`: the timer service reads main marks from the window configuration, whose snapshot ended at `code/willOpenNewWindow` before shell completion. A future exact main completion measurement needs a different capture mechanism; repeating delayed Startup Performance reports will not supply it.

A separate [focused V8 trace](../performance/v0.8.0-renderer-v8-cache-focused-diagnostic.json) identified the cold renderer cost more directly. A fresh isolated profile spent 435.583 ms parsing `workbench.desktop.main.js` on a background thread during a 564 ms workbench import. In an established isolated profile after one warm-up, Chromium accepted 11,685,400 bytes of V8 module code cache (`cacheRejected=false`), emitted no corresponding background-parse event, and the workbench import lasted 113 ms. These are one launch in each profile condition, not paired benchmark samples; the parse interval overlaps the import and cannot be added to it. The report's `cached data: NO` text is only an upstream heuristic based on a configured cache path and last-running commit, not a direct reading of Chromium's module cache. The app already registers `vscode-file` with `codeCache: true` and sets a per-commit Chromium cache path when configured, so merely enabling custom-protocol caching is not a new optimization. Future bundle-splitting work must state whether it helps first-run cold parsing, established-profile opening, or both.

The cache also changes which stage waits. In the fresh V8 launch, the renderer's shell-environment promise resolved 6 ms **before** extension-host allocation finished. In the warmed launch, allocation finished at epoch 1,790,676,401,666 ms, but the shell promise did not resolve until 1,790,676,401,936 ms: 270 ms later. Extension-host `fork/start` appeared another 67 ms after that, and the control extension activated normally. These raw renderer marks were captured after the Startup Performance report snapshot; that report omitted the warmed shell mark. The 270 ms is a single-launch gate, not 270 ms of available saving.

An [exact main-process shell trace](../performance/v0.8.0-main-shell-gate-focused-diagnostic.json) now uses an environment-gated log timestamp rather than the stale window-configuration snapshot. In one compact established-profile run, shell resolution began 270 ms after process spawn and took 741 ms. The renderer requested an extension host at 849 ms and its wrapper was allocated at 892 ms; main shell resolution finished at 1,011 ms, the renderer received it 3 ms later, and the host fork started at 1,076 ms. The installed control extension activated at 1,175 ms. Thus 119 ms elapsed between wrapper allocation and main shell completion in this run, followed by 65 ms to the actual fork. This confirms a shell gate exists but does not show that it can be removed safely. The extension activation marker is not the extension-editable-file endpoint, and one run cannot estimate p95. The full paired GUI suite remains off for this minor-release investigation.

A separate non-GUI `/bin/zsh -i -l -c` probe on the same Mac took 660–765 ms for a no-op and 667–718 ms when executing `/usr/bin/env -0` with output suppressed, three runs each. This suggests the user's login-shell initialization dominates the 741 ms main interval; the environment collector itself is relatively small. The probe is not a paired app comparison and does not justify skipping the configured shell environment for extensions or terminals.

An Astra architecture review rejected an early two-phase extension-host spawn under the requirement to preserve the final environment. `createExtensionHost()` only allocates a `WindowUtilityProcess` wrapper; the actual `utilityProcess.fork()` receives the final shell-derived environment. Electron/Node initialization and VS Code's bootstrap read environment values before an IPC message could patch `process.env`, so a spawned host waiting for a later environment message would not have equivalent native module, path, debug, or subprocess semantics. Restarting that early helper with the final environment discards its initialized runtime. Small environment-independent listener/options preparation can move before the existing `Promise.all` barrier, but has no demonstrated 100 ms saving. Keep the correct spawn barrier; investigate reducing shell-resolution time without changing extension behavior, and separately evaluate cold-only bundle reduction.

A follow-up architecture review also rejected persisting a previous login-shell environment to bypass this gate on later Finder launches. Shell startup may source arbitrary files or commands and produce time-dependent values; timestamps, TTLs, and selected dotfile fingerprints cannot prove a cached snapshot is current. A background correction would arrive after extensions, Git, terminals, or language servers may have used the old values, and a complete persisted environment would add secrets at rest. Main already starts the fresh resolver asynchronously soon after the primary-instance claim; moving that start to immediately after `claimInstance()` preserves semantics but earlier trace marks allow only a small overlap, not a 741 ms saving. Retain the fresh pre-fork environment and reconsider that relocation only with evidence that the intervening work has grown materially.

## Three gated experiments

| Candidate | Admission and focused evidence | Stop condition |
| --- | --- | --- |
| Preload the existing workbench module before bootstrap imports it | **Rejected and removed from source.** The [HTML standard](https://html.spec.whatwg.org/multipage/links.html#link-type-modulepreload) allows early module fetching without evaluation, and [Chrome's guidance](https://web.dev/articles/modulepreload) describes possible early parsing and compilation. The emitted 16,968,267-byte workbench module had zero static imports. In one matched fresh-profile trace, the candidate's workbench import took 593 ms versus 365 ms for control and control-extension activation was 62 ms later. In one separate extension-backed editable-file pair, candidate was 1,263.111 ms versus 1,257.292 ms for control: effectively neutral. [Sanitized data](../performance/v0.8.0-rejected-workbench-modulepreload-focused-diagnostic.json). | There was no directional file-ready benefit, and the trace was slower. The single pair cannot estimate p95 or a reliable effect; do not release or advertise this candidate. |
| Separate environment-independent extension-host bootstrap from shell-dependent initialization | **Rejected under current correctness constraints.** Focused launches found 107 ms of renderer shell-promise wait after host allocation in one cold run and 270 ms in a warmed-profile run, but allocation is only a wrapper, not an already-running utility process. The real fork requires the final environment. | Patching `process.env` after Electron/Node initialization cannot reproduce spawning with the final environment. A safe early helper restarted with the final environment loses its initialized work. The earlier prewarm gained only 7–40 ms. Revisit only if a genuinely environment-independent, substantial bootstrap stage is proved; do not count the 465 ms wrapper-to-origin gap as recoverable time. |
| Lazy-load a substantial optional main-process implementation graph | First attribute at least 100 ms of fresh-profile startup CPU to separable eager application parsing or evaluation, then preserve synchronous IPC registration and first-event behavior. The 280 ms time-origin-to-main figure includes runtime startup and is not enough attribution. The 37 ms later main-run span does not exclude parsing earlier in the bundle. | Do not edit the main process merely to shrink packaged bytes or repeat the rejected main compile cache. Stop if a deferred import stays in the eager unsplit bundle, first requests slow materially, or MCP/extension contracts change. |

Omitting remaining Agent Host or diff-worker package resources can reduce disk size, but it is not an established stopped-process startup improvement. The focused trace waited for installed control-extension activation and used a compact bottom-left window. Chromium returned zero resource-timing entries for this custom app protocol, so it could not establish when the module fetch began or whether it duplicated. The trace's activation endpoint is separate from the editable-file probe. Neither the single trace pair nor the single editable-file pair is a full benchmark.

For that focused A/B check, a local control app was cloned from the unsigned v0.8 candidate and only the preload comment and link were removed from its packaged `workbench.html`. A symlink-safe SHA-256 inventory compared 2,196 bundle paths and found exactly that one changed file; both apps have the same ad-hoc linker signature state. The control is a disposable `.build/lean-artifacts/LeanVSCode-v08-control-darwin-arm64/Lean VS Code.app`, not a release artifact or the original Code-OSS comparator used for public claims. The candidate workbench JavaScript also matches the installed v0.7 module in length and content apart from embedded commit and build-date text. An in-memory `vm.SourceTextModule` compile under the candidate's Electron 43.6.0/V8 15.0 took 216, 189, and 196 ms; this excludes loading, caching, evaluation, and app startup, so it is only a synthetic indication of parse cost, not a measured saving.

The fork currently pins Electron 43.6.0. [Electron 43's own release notes](https://www.electronjs.org/blog/electron-43-0) already list an embedded main-process Node startup snapshot, cached framework/preload bytecode, and earlier sandboxed-renderer startup data; [its detailed notes](https://releases.electronjs.org/release/v43.0.0) also list macOS ThinLTO. [Electron 44](https://www.electronjs.org/blog/electron-44-0) is available, but its published notes do not establish a further Apple Silicon file-ready improvement. Treat a runtime upgrade as a compatibility and upstream-update project with its own release gates, not as a v0.8 speed win by version number alone.

The [cold renderer split candidate](V0.8_COLD_RENDERER_SPLIT_DESIGN.md) removes about 3.17 MB from the initial unminified static graph while retaining service and extension API registrations. Six focused headless tests now cover the lazy Quick Chat proxy's queued first-use behavior, but its real UI has not been exercised. Startup diagnostics are inconclusive, so the split is held out of release. It chiefly targets the first cold launch; the warmed-profile shell wait needs its own safe approach.

Before any v0.8 release, keep only candidates with a measured directional benefit and passing edit/save, search, terminal, Git diff, installed extension and webview checks; verify signing, notarization, update ZIP, DMG, live update, and installation. If no candidate clears its gate, document the rejected trial and continue investigating instead of publishing an unsupported speed claim.
