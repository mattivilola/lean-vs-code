# v0.8 startup investigation

This is a development record, not a v0.8 release commitment or a measured speed claim. The signed v0.7.0 app remains the current release. The next target is a stopped-process file that accepts an extension-backed edit at p95 below one second, with editing, Git review, terminal, installed extensions, signing, and updating intact. Full paired GUI benchmarks run only for a major release or an explicit owner request; focused diagnostics for a minor-release experiment are separate from public speed claims.

## What the existing trace actually shows

The [sanitized admission record](../performance/v0.8.0-critical-path-admission.json) comes from an exploratory v0.7 trace with the subsequently removed main-process compile cache; it is useful for identifying work, not a signed-v0.7 timing baseline. It reports 120 ms to import `main.js`, 196 ms from `window.loadUrl()` to the renderer's workbench import, and another 120 ms to import the workbench. About 190 ms of the first renderer interval precedes workbench bootstrap execution. Blocking workbench contributions took 11 ms. “Extensions registered: 707 ms” is cumulative startup-to-registration time; the actual `register extensions & spawn extension host` span was 63 ms.

The shell collector starts at trace time 253 ms. Main services were created at 228–239 ms, initialized at 239–251 ms, and the primary-instance claim finished at 252 ms. Starting the same collector earlier after configuration and instance ownership offers only about 1–14 ms of overlap, so that proposal is rejected. The trace captured `willResolveShellEnv` but not shell completion; it does not establish the final v0.7 shell path's full critical-path cost. A previous extension-host prewarm prototype gained only 7–40 ms of lead and was removed.

Three retained, local v0.6 exploratory fresh-profile reports (product commit `0c349fe10c683500fb813278453f209b6f31d69b`) recorded workbench import spans of 719, 469, and 383 ms, each marked `cached data: NO`. Their window-load-to-import spans were 175, 230, and 168 ms. These old, single-app reports are not a v0.8 baseline or a paired speed result. They show why the preload experiment needs both fresh-profile and established-profile focused checks: moving a large uncached module fetch or parse may matter differently from the later 120 ms established-profile import. The raw reports contain local paths and remain unpublished.

## Three gated experiments

| Candidate | Admission and focused evidence | Stop condition |
| --- | --- | --- |
| Preload the existing workbench module before bootstrap imports it | A narrow `modulepreload` candidate is built on the v0.8 branch. The [HTML standard](https://html.spec.whatwg.org/multipage/links.html#link-type-modulepreload) fetches it into the module map without evaluating it; [Chrome's guidance](https://web.dev/articles/modulepreload) explains that it can also parse and compile the module before execution. Workbench execution remains behind window configuration and NLS setup. The minified package contains the linked 16,968,267-byte file, and parsing that emitted module found zero static imports, so this link does not recursively preload another module graph. Typecheck and `lean:check-ai` pass. A compact-window trace and feature smoke still need to show whether the 196 ms pre-import interval and extension-editable path improve. | Revert if Chromium already overlaps the resource, the preload competes for startup CPU, introduces an early execution/error path, or the focused file-ready endpoint does not improve without regressions. Do not infer a startup win from a valid link or smaller fetch interval alone. |
| Separate environment-independent extension-host bootstrap from shell-dependent initialization | Only attempt after a trace captures shell completion and attributes at least 100 ms of safely movable host startup. Preserve final `PATH`, native modules, subprocess inheritance, activation, trust, crash/restart, and multi-window isolation. | Do not implement if the safe independent segment is below 100 ms or the earlier 7–40 ms prewarm result remains representative. A 445 ms allocation-to-process gap is not automatically recoverable time. |
| Lazy-load a substantial optional main-process implementation graph | First attribute at least 100 ms to separable eager work in an emitted bundle/profile, then preserve synchronous IPC registration and first-event behavior. The whole measured main import is only 120 ms, so this is currently a research candidate. | Do not edit the main process merely to shrink packaged bytes or repeat the rejected main compile cache. Stop if an eager shared chunk remains, first requests slow materially, or MCP/extension contracts change. |

Omitting remaining Agent Host or diff-worker package resources can reduce disk size, but it is not an established stopped-process startup improvement. The next diagnostic trace waits for installed control-extension activation, so it can retain shell and extension-host marks that an earlier `didLoadExtensions`-only snapshot missed. It seeds the same small bottom-left window as other focused GUI checks. Check the preload in both fresh and established isolated profiles, and inspect the resource timing relative to `code/willLoadWorkbenchMain`; an earlier fetch alone does not prove earlier file readiness. Do not run it against a live user session or present its isolated samples as a full benchmark.

The fork currently pins Electron 43.6.0. [Electron 43's own release notes](https://www.electronjs.org/blog/electron-43-0) already list an embedded main-process Node startup snapshot, cached framework/preload bytecode, and earlier sandboxed-renderer startup data; [its detailed notes](https://releases.electronjs.org/release/v43.0.0) also list macOS ThinLTO. [Electron 44](https://www.electronjs.org/blog/electron-44-0) is available, but its published notes do not establish a further Apple Silicon file-ready improvement. Treat a runtime upgrade as a compatibility and upstream-update project with its own release gates, not as a v0.8 speed win by version number alone.

Before any v0.8 release, keep only candidates with a measured directional benefit and passing edit/save, search, terminal, Git diff, installed extension and webview checks; verify signing, notarization, update ZIP, DMG, live update, and installation. If no candidate clears its gate, document the rejected trial and continue investigating instead of publishing an unsupported speed claim.
