# v0.8 cold renderer split candidate

This design is now implemented as an unsigned candidate, not a shipped optimization or public speed claim. The [focused Chromium trace](../performance/v0.8.0-renderer-v8-cache-focused-diagnostic.json) attributes 435.583 ms to background parsing of the 16.9 MB minified desktop workbench module in one fresh-profile launch. After one warm-up, Chromium accepted its module cache and the import took 113 ms in a separate launch. Splitting unused chat UI is therefore a **cold-start parse** candidate; it does not solve the warmed-profile shell-environment gate or establish a normal-launch gain. Full paired GUI benchmarks remain reserved for major releases or an explicit request.

## Candidate boundary

The existing desktop esbuild metafile reports approximately 5.25 MB of chat contribution source in the unminified initial bundle. An Astra read-only reverse-graph review modeled ten import-edge cuts across nine importer files. Together they would remove about 3.02 MB of chat code and 3.29 MB total JavaScript from the **initial static graph**. These are `bytesInOutput` estimates, not emitted split-bundle sizes or startup savings. The four simpler groups alone remove only 271 KB; the large gain requires the Quick Chat service to stop importing its rendering implementation at startup.

1. Keep `IQuickChatService` registered synchronously, but make its implementation load `chatQuick.ts` on first use. Preserve the interface's synchronous methods and getters with a small proxy. Queue or coalesce operations while loading, cancel pending opens on close/dispose, preserve `onDidClose`, and handle load errors. First-use Quick Chat behavior needs focused checks for repeated toggle, a query arriving during load, close-before-load, and focus. The existing `QuickChatService.open()` returns `void` and establishes UI immediately, so this boundary is the principal compatibility risk.
2. In `chatAccessibilityProvider.ts`, import the two action ID strings from a lightweight constants module rather than `chatExecuteActions.ts` and `chatToolActions.ts`; re-export the old names from those action modules.
3. In `chatWidgetService.ts`, retain type-only `IChatEditorOptions` but load `ChatEditor` inside its two existing async methods before their `instanceof` checks.
4. In `gettingStarted.contribution.ts`, read the Agent Sessions welcome command ID from a small constants module instead of importing the page implementation.
5. In six interactive, REPL, and notebook callers, replace static `InlineChatController.get(editor)` imports with a lightweight `editor.getContribution(INLINE_CHAT_ID)` helper and type-only controller imports. Keep the controller registration unchanged.
6. Enable ESM splitting for the desktop workbench entry in `build/next/index.ts`. Inspect **every transitively static initial chunk**, not only `workbench.desktop.main.js`; the previous split emitted a large eager shared chunk and no file-ready gain. Verify packaging, source maps, CSS, NLS, asset paths, and signing after the graph change.

Keep the current Lean AI service registrations and all extension-host API actors intact. `npm run lean:check-ai` now follows every transitively static output chunk and proves service registrations and all 87 actors. The [candidate measurements](../performance/v0.8.0-cold-renderer-split-candidate.json) show 31,755,997 versus 34,929,026 unminified initial static JavaScript bytes, a 3,173,029-byte reduction. The production-minified packaged app's initial static JavaScript is 15,397,330 bytes versus 16,968,267 in installed v0.7.0, a 1,570,937-byte reduction. The candidate still packages 1,529,484 bytes of optional JavaScript chunks, so this is **not an installed-app disk-size saving**. It is an internal historical comparison, not a Code-OSS claim or a startup timing.

Typecheck, changed-file lint, the AI/DI/actor guard, and the production-minified build passed. One compact 560 × 360 isolated-profile functional check passed edit/save, file and text search, terminal, Git diff, and extension webview. The packaged local app needed an ad-hoc signature for this test; it is not a Developer ID release. A focused candidate trace recorded a 635 ms workbench import, versus 564 ms in an earlier, unpaired control trace. A three-pair candidate-versus-installed-v0.7 diagnostic produced only two complete pairs because the v0.7 app timed out once; the candidate was slower in one complete pair and 10 ms faster in the other. Neither observation demonstrates a speed gain. The trace's custom-protocol resource timings were empty, so it did not prove whether optional chunks were fetched before file readiness.

Architecture review found that the initial lazy proxy bypassed `QuickChatService.toggle()`'s partial-query cleanup and could drop an earlier query while loading. The proxy now replays pending operations in order and cancels the queue on close/dispose. Six focused headless Chromium unit cases passed for partial-query and repeated toggles, queued query/focus, close/reopen, disposal, and load failure. Typecheck, changed-file lint, and the AI/DI/actor guard also passed. These tests exercise the proxy with a controlled async import, not the real first-use Quick Chat UI. Hold this split out of release until an installed extension, first-use Quick Chat, packaging, signing, and a focused no-regression comparison pass. Do not publish a speed percentage without the matched signed Code-OSS comparison allowed by release policy.
