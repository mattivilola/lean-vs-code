# v0.8 cold renderer split candidate

This is an implementation design, not a shipped optimization or public speed claim. The [focused Chromium trace](../performance/v0.8.0-renderer-v8-cache-focused-diagnostic.json) attributes 435.583 ms to background parsing of the 16.9 MB minified desktop workbench module in one fresh-profile launch. After one warm-up, Chromium accepted its module cache and the import took 113 ms in a separate launch. Splitting unused chat UI is therefore a **cold-start and bundle-footprint** candidate; it does not solve the warmed-profile shell-environment gate or establish a normal-launch gain. Full paired GUI benchmarks remain reserved for major releases or an explicit request.

## Candidate boundary

The existing desktop esbuild metafile reports approximately 5.25 MB of chat contribution source in the unminified initial bundle. An Astra read-only reverse-graph review modeled ten import-edge cuts across nine importer files. Together they would remove about 3.02 MB of chat code and 3.29 MB total JavaScript from the **initial static graph**. These are `bytesInOutput` estimates, not emitted split-bundle sizes or startup savings. The four simpler groups alone remove only 271 KB; the large gain requires the Quick Chat service to stop importing its rendering implementation at startup.

1. Keep `IQuickChatService` registered synchronously, but make its implementation load `chatQuick.ts` on first use. Preserve the interface's synchronous methods and getters with a small proxy. Queue or coalesce operations while loading, cancel pending opens on close/dispose, preserve `onDidClose`, and handle load errors. First-use Quick Chat behavior needs focused checks for repeated toggle, a query arriving during load, close-before-load, and focus. The existing `QuickChatService.open()` returns `void` and establishes UI immediately, so this boundary is the principal compatibility risk.
2. In `chatAccessibilityProvider.ts`, import the two action ID strings from a lightweight constants module rather than `chatExecuteActions.ts` and `chatToolActions.ts`; re-export the old names from those action modules.
3. In `chatWidgetService.ts`, retain type-only `IChatEditorOptions` but load `ChatEditor` inside its two existing async methods before their `instanceof` checks.
4. In `gettingStarted.contribution.ts`, read the Agent Sessions welcome command ID from a small constants module instead of importing the page implementation.
5. In five interactive, REPL, and notebook callers, replace static `InlineChatController.get(editor)` imports with a lightweight `editor.getContribution(INLINE_CHAT_ID)` helper and type-only controller imports. Keep the controller registration unchanged.
6. Enable ESM splitting for the desktop workbench entry in `build/next/index.ts`. Inspect **every transitively static initial chunk**, not only `workbench.desktop.main.js`; the previous split emitted a large eager shared chunk and no file-ready gain. Verify packaging, source maps, CSS, NLS, asset paths, and signing after the graph change.

Keep the current Lean AI service registrations and all extension-host API actors intact. `npm run lean:check-ai` must continue to prove service registrations and all 87 actors; its bundle audit may need to follow split outputs. A candidate is worth retaining only if the actual minified, packaged **initial** chunk graph shrinks substantially (target about 3 MB unminified-equivalent), optional chunks are not fetched before file readiness, and focused editing, installed-extension activation, Git review, terminal, webview, and first-use chat/API checks pass. A small diagnostic may assess direction, but do not publish a speed percentage without the matched signed Code-OSS comparison allowed by release policy.
