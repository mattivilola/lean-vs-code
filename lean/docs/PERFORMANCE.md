# Performance and version history

Lean VS Code's public performance comparison is **always against original Code-OSS 1.139.1 source at the fork's base revision** (`04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1`). The successfully measured Code-OSS package used the **unminified** build task; starting with v0.4.0, Lean's release uses the production-minified task. The v0.4.0-versus-Code-OSS percentage therefore includes a build-mode difference and is not a like-for-like optimized-distribution comparison. Direct Lean-version trials below are retained only to diagnose changes and regressions, not as the public speed claim. The reference Mac is an Apple M3 Max with 36 GiB of RAM running macOS 27.0.0. These are measured results on that machine, not guarantees for every project or Mac.

**Benchmark cadence:** Run the full paired comparison for each new minor release (`x.y.0`) against original Code-OSS built from the same upstream revision, and retain earlier minor-release results for history. Routine patch releases (`x.y.z`, where `z > 0`) do not need a new full comparison. Keep the latest minor release's figures labeled with the exact version measured; do not present them as measurements of a later patch. Run a targeted performance check for a suspected regression, a performance-sensitive patch, or an explicit request. Functional, update, signing, and packaging checks still apply to every release. Direct Lean-version trials can help diagnose a change, but public percentage claims use the paired Code-OSS baseline.

The v0.4.0-versus-Code-OSS row is the public source-baseline comparison, subject to the build-mode caveat above. An optimized Code-OSS package was built from the same upstream revision, but its upstream packaging task omitted runtime assets and the locally repaired comparator did not reach the requested editor reliably on repeated launches. No numbers from that invalid trial are published as a speed comparison.

The [separate 10,000-file Git-workspace trial](../performance/v0.4.0-git-workspace-vs-code-oss-1.139.1.json) opened a tracked file with its repository. Across 30 paired launches, signed Lean v0.4.0 reached an editable file in **1,437 / 1,475 ms** median / p95 versus **1,829 / 1,943 ms** for the original Code-OSS source build: **21% less median time** and **24% less p95 time**. Existing-window file opens were **362 / 390 ms** for Lean and **372 / 415 ms** for Code-OSS; these small differences should not be generalized without further runs. This source-baseline comparison has the same optimized-versus-unminified build caveat as the standalone-file trial. Three idle-memory readings per app came from only **one launch each**, so the 553 versus 952 MiB medians do not establish a durable memory saving; collect multiple independent launches before making such a claim.

The [first-use Git-review workflow trial](../performance/v0.4.0-git-review-vs-code-oss-1.139.1.json) started each app with an isolated one-file Git repository, waited for the requested file to become the active editor, opened Source Control, waited for the bundled Git extension to discover the repository, and read its local diff through the Git API. In 30 alternating pairs, **stopped-process launch to completed diff retrieval** was **1,492 / 1,557 ms** median / p95 for signed Lean v0.4.0 and **2,002 / 2,060 ms** for original Code-OSS: **25% less median time** and **24% less p95 time**. The metric uses wall-clock timestamps across the launcher and temporary `onStartupFinished` extension; it is not a key-to-painted-diff measurement. Inside that extension, the Git action alone was **130 / 152 ms** for Lean versus **50 / 75 ms** for Code-OSS. This slower first Git action is a real tradeoff of demand-driven activation and is included in the faster end-to-end result. The same minified-versus-unminified build caveat applies. Editing and saving, search, a shell command in the integrated terminal, Git diff access, and extension webview creation passed isolated GUI checks on both apps after the timing run.

The workflow harness also supports first-use search, terminal, edit-and-save, and extension-webview scenarios. Short exploratory search and terminal runs did **not** establish a Lean speed advantage; they are not public speed claims. Candidate claims need at least 30 paired launches, the same Code-OSS base, a useful completed-work endpoint, retained failures, and clear build provenance. Large files, multi-root workspaces, reopening an existing window, and multi-extension projects are useful future workloads, but none has a measured speed claim beyond the existing-window and Git-repository results above.

In this direct 30-pair run, v0.4.0 reduced median file-ready time by **5%** and p95 by **6%**. The already-open-window median was 8 ms slower, so no second-file speedup is claimed. The three idle-memory snapshots came from **one launch per app**; v0.4.0's median was 7% higher in this run. The identical v0.4.0 bundle measured 650 MiB in the separate Code-OSS run, revealing substantial between-run variation. These data do not support a v0.4.0 memory-saving claim. Future memory comparisons should use multiple independent launches as well as within-launch snapshots.

The v0.2.0 and v0.3.0 rows preserve separate paired trials against the original Code-OSS baseline, so their percentages use the Code-OSS result **from the same run**. Differences between those two Lean rows alone are not a controlled version-to-version effect. The development candidate's [same-run comparison with v0.2.0](../performance/v0.3.0-candidate-vs-v0.2.0.json) showed under 1% median startup difference for a standalone file. In a generated repository with 10,000 tracked files, the [candidate versus v0.2.0 comparison](../performance/v0.3.0-candidate-git-vs-v0.2.0.json) showed no repository-open startup improvement: 1,662 ms versus 1,652 ms median. Git activation is now demand-driven, but it should not be advertised as a measured file-ready speedup. The [earlier candidate versus Code-OSS trial](../performance/v0.3.0-candidate-vs-code-oss-1.139.1.json) remains available as development evidence; public headline numbers use the signed release trial.

The harness alternates product order over **30 warm-cache launches per product** and 30 file opens in existing windows. Each launch gets isolated user-data, shared-data, and extension directories. Both apps load the same small benchmark control extension, which marks a 100 KiB text file ready after it becomes the active editor and passes a reversible edit probe. The file-open measure starts when the app CLI is invoked with `--reuse-window`. Three memory snapshots follow 30 seconds of idle time. For each app process and child, the harness reads macOS `footprint`'s `phys_footprint` and sums those readings. Shared pages can appear in more than one process's accounting; this is a comparative app-tree measure, not a unique-physical-pages count or the memory used by every possible extension. [Harness instructions](../../scripts/lean-perf/README.md) explain how to repeat it.

The measured Code-OSS baseline was built from the exact upstream source revision with the unminified packaging task. Its packaging task omitted the Copilot SDK directory, so that directory was copied from the same revision's installed source dependencies into the otherwise built app before ad-hoc signing for the local trial. This repairs a packaging omission without changing the source behavior; it is still a source-built comparison, not a stock Microsoft Visual Studio Code release. The v0.2.0 app was the signed installed release. The v0.3.0 final run used the signed and notarized release bundle extracted from the DMG built from fork commit `13fbbf8e65a1733a0b03ce47111d2f1a00c31b02`. v0.4.0 was measured from the signed and notarized update ZIP whose app content matches its DMG exactly.

These runs do **not** establish true cold-cache launch time, peak memory, large-file performance, long-session leak freedom, or universal extension compatibility. The original plan's 1-second file-ready and 250 MiB idle targets remain unmet. The v0.4.0 signed release reached 1,268 ms p95 in the direct comparison. Further reductions need profiling of the renderer's initial bundle and extension-host startup, then narrow changes that retain API registration and feature behavior. Broadly removing AI/MCP contributions now would risk extension services without a demonstrated net memory benefit.

The [startup roadmap](STARTUP_ROADMAP.md) records the original research proposals, the changed v0.4 implementation, and candidates for further Apple Silicon and Electron experiments. Projected changes remain hypotheses until measured in a signed release.
