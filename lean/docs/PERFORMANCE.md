# Performance and version history

Lean VS Code's public performance comparison is **always against original Code-OSS 1.139.1 source at the fork's base revision** (`04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1`). The v0.6.0 speed comparisons and v0.7.0–v0.8.0 package-size comparisons use **minified builds for both apps**. Code-OSS is a locally repaired source package, not the official Microsoft VS Code distribution; the repair supplies a runtime dependency from the same upstream source dependencies without changing its source code. Earlier unminified Code-OSS trials remain labeled as historical measurements, not the current headline. Direct Lean-version trials below are retained only to diagnose changes and regressions. The reference Mac is an Apple M3 Max with 36 GiB of RAM running macOS 27.0.0. These are measured results on that machine, not guarantees for every project or Mac.

**v0.8.0 signed-release package size:** The [signed app-bundle comparison](../performance/v0.8.0-bundle-size-vs-code-oss-1.139.1-minified.json) measures **514 versus 1,463 MiB** of apparent content against the original same-revision minified Code-OSS source package: **64.9% smaller**. It is a direct package measurement, not a GUI startup, download-size, or runtime-memory result. The [signed-app functional checks](../performance/v0.8.0-release-functional-no-timing.json) passed without timing collection. No new v0.8.0 speed or memory percentage is claimed; earlier results remain version-labeled.

**v0.7.0 signed-release package size:** The [signed app-bundle comparison](../performance/v0.7.0-bundle-size-vs-code-oss-1.139.1-minified.json) measures **513 versus 1,463 MiB** of apparent content against the original same-revision minified Code-OSS source package: **64.9% smaller**. It is a direct package measurement, not a GUI startup, download-size, or runtime-memory result. The full paired GUI suite was stopped at the owner's request; no partial observations are used, and no new v0.7.0 speed percentage is claimed. Earlier results below remain version-labeled.

**v0.6.0 signed-release result:** In [30 alternating first saved-edit pairs](../performance/v0.6.0-signed-first-save-vs-code-oss-1.139.1-minified.json), the signed Lean app completed process start, file open, first edit, save, and on-disk verification in **1,468 / 1,912 ms median / p95** versus **1,959 / 2,640 ms** for the original, same-revision minified Code-OSS source build. All 60 timed launches succeeded. The median full-workflow saving was **491 ms / 25%**, while the edit/save action after startup was slower in Lean (**86.3 versus 43.3 ms median**). The signed v0.6.0 [installed bundle](../performance/v0.6.0-bundle-size-vs-code-oss-1.139.1-minified.json) was **535 versus 1,463 MiB** of apparent content, **63.4% smaller**. This is not a runtime-memory comparison.

The earlier [v0.6 candidate extension-backed file](../performance/v0.6.0-candidate-extension-fresh-vs-code-oss-1.139.1-minified.json) and [Finder first synthetic edit](../performance/v0.6.0-candidate-first-ui-edit-finder-vs-code-oss-1.139.1-minified.json) trials used unsigned minified commit `48da33a` before the light theme; they are labeled candidate results, not a signed-release startup claim. The signed app passed the representative GUI feature smoke and macOS trust checks. A later signed extension-backed benchmark was stopped at the user's request when it began the existing-window phase; no incomplete observations are used as a public claim. A new independent-launch v0.6 memory trial was not run.

**Benchmark cadence:** Run the full paired GUI comparison against original same-revision Code-OSS only for a major release or when the owner explicitly requests it. Minor and patch releases use focused regression checks. Keep earlier results labeled with the exact Lean version and workload measured; never silently apply them to a later version. Without a new matched run, make no new speed or memory percentage claim for that release. Editing, review, extension, update, signing, and packaging gates still apply to every release. A direct packaged-bundle size measurement is separate from the full GUI suite. Direct Lean-version trials help diagnose changes but are not public Code-OSS speed claims.

The [signed v0.5.0 paired release run](../performance/v0.5.0-vs-code-oss-1.139.1-minified.json) completed all 60 stopped-process editability checks and all 60 already-running-window checks. Its 307 ms median stopped-process advantage is about 16% of the same-run Code-OSS median. The 2,009 ms p95 remains well above the 1,000 ms goal. The signed app was extracted from the notarized update ZIP; every app file and symlink target matched the DMG. Different sessions have produced different absolute baselines, so the v0.5.0 percentage is calculated only against its simultaneous Code-OSS run. The [v0.5.0 bundle report](../performance/v0.5.0-bundle-size-vs-code-oss-1.139.1-minified.json) shows 63.2% less apparent installed content; it does not measure a download-size difference.

The optimized Code-OSS package originally failed the file-ready probe, so its first attempted trial was discarded. With the same runtime dependency repair and a clean isolated GUI launch, it later passed editing and saving, search, terminal, Git diff, and extension webview checks; the new 30-pair trial above completed without failed samples. Its local ad-hoc signature and dependency repair mean it is a source-build baseline, not a distributable official VS Code package. The [earlier unminified paired run](../performance/v0.4.0-vs-code-oss-1.139.1.json) measured 1,262 / 1,310 ms for Lean versus 1,608 / 1,727 ms for Code-OSS, a 22% median difference with a build-mode mismatch. It is preserved for audit but no longer leads the public comparison.

The [packaged app-bundle size report](../performance/v0.4.0-bundle-size-vs-code-oss-1.139.1-minified.json) measured the installed signed v0.4.0 app and the same-revision, locally repaired minified Code-OSS source package on the same Mac. macOS `du -A -sk` reported **537.8 MiB versus 1,462.9 MiB** of apparent app-bundle content, **63.2% less** for Lean; `du -sk` reported 541.3 versus 1,518.4 MiB allocated on this filesystem. The bundle contains 33 versus 96 bundled extension directories and 50 versus 8,915 `.map` files. These categories help explain the difference, but the report does not attribute a separate percentage to any one packaging change. The signed/notarized Lean v0.4.0 DMG is **206,823,232 bytes (206.8 MB)**, verified against its release SHA-256. There is no matched Code-OSS DMG in this comparison, so no download-image-size percentage is claimed. App-bundle size does **not** measure running memory, user data, or later installed extensions; this comparator is a source package, not Microsoft's distributed VS Code app.

The [independent-launch idle-memory trial](../performance/v0.4.0-independent-memory-vs-code-oss-1.139.1-minified.json) used **nine fresh-profile launches per app** in one uninterrupted awake period, alternating which product's memory session ran first. After an editable 100 KiB file and the same temporary control extension were ready, each app idled for 30 seconds. macOS `footprint`'s per-process `phys_footprint` values were summed across the observed app tree. Signed Lean v0.4.0 measured **687,172,408 bytes (655.3 MiB) median** versus **824,652,880 bytes (786.5 MiB)** for minified original Code-OSS: **16.7% less median short-idle app-tree footprint**. Lean was lower in **all nine pairs**; its range was 651.6–660.2 MiB and Code-OSS's was 779.7–791.2 MiB. The power log showed a full wake before the first included sample and no sleep until after the final sample. An earlier pilot pair, separated by a system sleep, was excluded from this public result. The comparator had nine observed processes versus Lean's seven in each included pair; process count is part of this fixture's result, not a universal property. Summing billed footprints can count shared pages more than once, and this test does not establish peak use, long-session behavior, or memory with a user's installed extensions. Earlier one-launch memory readings varied enough that they remain diagnostics rather than the basis of this claim.

An additional [established-profile trial](../performance/v0.4.0-persistent-profile-vs-code-oss-1.139.1-minified.json) reused each app's own isolated profile after one warm-up, while fully stopping the app between timed launches. In 30 alternating pairs, signed Lean v0.4.0 reached an editable 100 KiB file in **1,413 / 1,460 ms** median / p95 versus **1,461 / 1,502 ms** for the same-revision minified Code-OSS source build: **3% less median time**, with Lean faster in **23 of 30 pairs**. Already-open-window file opens were **347 / 363 ms** for Lean versus **354 / 388 ms** for Code-OSS. The original fresh-profile run above found 17% less median startup time; its cache and profile condition is different and its percentage should not be applied to daily repeated starts. All 60 timed startup launches passed. The run also recorded one short-idle process-tree footprint snapshot per app, at 1,063,397,984 versus 1,374,876,992 bytes, but one launch per product cannot establish a repeatable memory gain. An earlier five-pair exploratory run agreed directionally; it is not used for this claim. A first attempt under restricted process access aborted both apps before readiness and is excluded; the complete rerun used macOS process access and `caffeinate`.

The [separate 10,000-file Git-workspace trial](../performance/v0.4.0-git-workspace-vs-code-oss-1.139.1-minified.json) opened a tracked file with its repository. Across 30 paired launches, signed Lean v0.4.0 reached an editable file in **1,482 / 1,687 ms** median / p95 versus **1,827 / 2,180 ms** for the minified original Code-OSS source build: **19% less median time** and **23% less p95 time**. Existing-window file opens were **363 / 409 ms** for Lean and **374 / 397 ms** for Code-OSS; the p95 moves in the other direction, so no existing-window speedup is claimed. Three idle-memory readings per app came from only **one launch each**, so their 702 versus 791 MiB medians do not establish a durable memory saving. The [earlier unminified repository trial](../performance/v0.4.0-git-workspace-vs-code-oss-1.139.1.json) is retained as historical evidence rather than the headline.

The [first-use Git-review workflow trial](../performance/v0.4.0-git-review-vs-code-oss-1.139.1-minified.json) started each app with an isolated one-file Git repository, waited for the requested file to become the active editor, opened Source Control, waited for the bundled Git extension to discover the repository, and read its local diff through the Git API. In 30 alternating pairs, **stopped-process launch to completed diff retrieval** was **1,497 / 1,672 ms** median / p95 for signed Lean v0.4.0 and **1,906 / 2,105 ms** for minified original Code-OSS: **21% less median time** and **21% less p95 time**. The metric uses wall-clock timestamps across the launcher and temporary `onStartupFinished` extension; it is not a key-to-painted-diff measurement. Inside that extension, the Git action alone was **135 / 177 ms** for Lean versus **56 / 74 ms** for Code-OSS. This slower first Git action is a real tradeoff of demand-driven activation and is included in the faster end-to-end result. Editing and saving, search, a shell command in the integrated terminal, Git diff access, and extension webview creation passed isolated GUI checks on both apps. The [earlier unminified workflow trial](../performance/v0.4.0-git-review-vs-code-oss-1.139.1.json) remains available for audit.

The [first saved edit trial](../performance/v0.4.0-edit-save-vs-code-oss-1.139.1-minified.json) measured from a stopped process until the requested document accepted an insertion, saved, and its changed bytes were verified on disk. The fixture was restored **after** the completion timestamp. In 30 alternating pairs, signed Lean v0.4.0 finished in **1,425 / 1,693 ms** median / p95 versus **1,901 / 1,946 ms** for minified original Code-OSS: **25% less median time** and **13% less p95 time**. All 60 trials passed, and Lean finished first in all 30 pairs. The action after startup measured **36 / 85 ms** for Lean versus **45 / 81 ms** for Code-OSS; its p95 moved in the other direction, so the public claim is about the full launch-to-save workflow, not consistently faster saving. An initial exploratory run included fixture restoration in its timestamp; that run was discarded before this corrected measurement. This one-file isolated-profile workflow is not a large-file or real-project save test.

The [first integrated-terminal command trial](../performance/v0.4.0-terminal-vs-code-oss-1.139.1-minified.json) measured from a stopped process until a shell command in the integrated terminal wrote a marker that the temporary extension verified on disk. In 30 alternating pairs, signed Lean v0.4.0 finished in **3,116 / 3,262 ms** median / p95 versus **3,598 / 3,701 ms** for minified original Code-OSS: **13% less median time** and **12% less p95 time**. All 60 runs passed, and Lean finished first in all 30 pairs. The action timed inside the extension after startup was **1,906 / 1,979 ms** for Lean versus **1,975 / 2,082 ms** for Code-OSS; most of the full-workflow difference came before that action. A preceding trial had three timeouts after macOS entered idle sleep and was excluded. The repeat used `caffeinate -dimsu` throughout; the power log showed no sleep during its nine-minute sample window. This measures a shell-command result, not the first painted terminal prompt or every shell configuration.

The [verified workspace text-search trial](../performance/v0.4.0-workspace-search-vs-code-oss-1.139.1-minified.json) used a 400-source-file Git fixture with 10 expected matches. The same proposed `findTextInFiles` API was enabled for the temporary control extension in both apps; completion required all 10 matches in the source folder. Across 30 alternating pairs, signed Lean v0.4.0 finished in **1,242 / 1,288 ms** median / p95 from launch versus **1,665 / 1,759 ms** for minified original Code-OSS: **25% less median time** and **27% less p95 time**. All 60 runs passed, and Lean finished first in all 30 pairs. The search action after startup measured **29 / 42 ms** for Lean versus **36 / 59 ms** for Code-OSS. This proves a first text-search result workflow through the extension API, not when a user sees results painted in the Search panel. The Mac stayed awake through the recorded samples; its next idle-sleep event began afterward.

A separate [first-visible-file diagnostic](../performance/v0.4.0-visible-file-vs-code-oss-1.139.1-minified.json) launched each app with a unique text fixture and used Chrome DevTools Protocol polling to detect that text in a nonzero-size Monaco editor DOM element. Across 30 alternating timed pairs after one warm-up per app, signed Lean v0.4.0 measured **999 / 1,073 ms** median / p95 versus **1,115 / 1,134 ms** for minified original Code-OSS: **10% less median time** and **5% less p95 time**. All 60 timed launches passed; Lean was faster in 29 pairs. One 1,723 ms Lean sample is retained in the raw report. Both apps used the same remote-debugging instrumentation, and macOS did not sleep during the run. DOM visibility is a proxy for content appearing, **not** verified display paint, focus, typing readiness, or an extension-backed edit. This diagnostic does not meet the primary p95 ≤ 1,000 ms editable-file target; even its own p95 is above one second.

The [first UI edit diagnostic](../performance/v0.4.0-first-ui-edit-vs-code-oss-1.139.1-minified.json) extended the same Chrome DevTools Protocol method: after finding the requested file's unique marker in a visible-size Monaco editor, it focused Monaco's native EditContext, sent unique synthetic text, and required that text to appear in the editor's visible lines. The fixture was not saved. Across 30 alternating pairs after one warm-up per app, signed Lean v0.4.0 reached this endpoint in **1,203 / 1,248 ms** median / p95 versus **1,334 / 1,368 ms** for minified original Code-OSS: **10% less median time** and **9% less p95 time**. All 60 timed launches passed; Lean was faster in all 30 pairs. Both apps used the same remote-debugging port and 20 ms polling, with macOS sleep prevented throughout. This is a synthetic UI edit verified through the DOM, not a physical key-to-paint timestamp, saved edit, or proof that an extension can edit. Its p95 remains above one second, and the primary extension-backed file-ready target remains unmet.

The [second-project-window first UI edit diagnostic](../performance/v0.4.0-second-project-window-vs-code-oss-1.139.1-minified.json) opened a file in one project-folder window, then used the same app instance and isolated profile to open a **distinct project folder** in another window. Timing started at the second-window CLI spawn and stopped when synthetic input appeared in the second file's visible Monaco editor lines. Across 30 alternating pairs after one warm-up per app, signed Lean v0.4.0 measured **901 / 1,147 ms** median / p95 versus **1,177 / 1,348 ms** for original minified Code-OSS: **23% less median time** and **15% less p95 time**. All 60 timed trials passed, with Lean faster in all 30 pairs. The first window's readiness time is retained in the raw observations but excluded from this interval. A preliminary 30-pair run opened loose files rather than two project folders; it is retained only as an internal diagnostic, and its 801 / 1,000 ms medians are not the project-window claim. This test verifies synthetic UI input in an already-running app, not a physical keypress, saved file, extension-backed readiness, or continued responsiveness of the first window. It does not measure stopped-process startup, so it must not be combined with the primary file-ready percentage.

The [developer workflow benchmark matrix](BENCHMARK_MATRIX.md) defines completed-work endpoints for future trials. The older `workspaceSearch` smoke still only opens its UI and must not be used as a result or paint claim; `workspaceTextSearch` verifies actual matches through the proposed API. The extension-webview smoke only creates a panel and assigns HTML, so a content-ready probe is still needed there. Candidate claims need at least 30 paired launches, the same Code-OSS base, a useful completed-work endpoint, retained failures, and clear build provenance. Large files, multi-root workspaces, reopening an existing window, and multi-extension projects are useful future workloads without a measured speed claim yet.

The v0.2.0 and v0.3.0 rows preserve separate paired trials against the original Code-OSS baseline, so their percentages use the Code-OSS result **from the same run**. Differences between those two Lean rows alone are not a controlled version-to-version effect. The development candidate's [same-run comparison with v0.2.0](../performance/v0.3.0-candidate-vs-v0.2.0.json) showed under 1% median startup difference for a standalone file. In a generated repository with 10,000 tracked files, the [candidate versus v0.2.0 comparison](../performance/v0.3.0-candidate-git-vs-v0.2.0.json) showed no repository-open startup improvement: 1,662 ms versus 1,652 ms median. The harness alternates product order over **30 warm-cache launches per product** and 30 file opens in existing windows. Each launch gets isolated user-data, shared-data, and extension directories. Both apps load the same small benchmark control extension, which marks a 100 KiB text file ready after it becomes the active editor and passes a reversible edit probe. The file-open measure starts when the app CLI is invoked with `--reuse-window`. Three memory snapshots follow 30 seconds of idle time. For each app process and child, the harness reads macOS `footprint`'s `phys_footprint` and sums those readings. Shared pages can appear in more than one process's accounting; this is a comparative app-tree measure, not a unique-physical-pages count or the memory used by every possible extension. [Harness instructions](../../scripts/lean-perf/README.md) explain how to repeat it.

The Code-OSS baselines were built from the exact upstream source revision. Earlier runs used its unminified packaging task; the current v0.6.0 comparison uses the minified task, matching Lean's build mode. Upstream packaging omitted the Copilot SDK directory, so a link to that directory in the same revision's installed source dependencies was added before ad-hoc signing the local minified comparator. This repairs a packaging omission without changing Code-OSS source behavior; it is still a source-built comparison, not a stock Microsoft Visual Studio Code release. The v0.2.0 app was the signed installed release. The v0.3.0 final run used the signed and notarized release bundle extracted from the DMG built from fork commit `13fbbf8e65a1733a0b03ce47111d2f1a00c31b02`. v0.4.0 was measured from the installed signed and notarized release, whose app content matches its update ZIP and DMG. v0.5.0 was measured from the signed and notarized update ZIP; its app content matches the DMG. The v0.6.0 saved-edit trial used the signed and notarized update ZIP app; its app content matches the v0.6.0 DMG.

These runs do **not** establish true cold-cache launch time, peak memory, large-file performance, long-session leak freedom, or universal extension compatibility. The original plan's 1-second file-ready and 250 MiB idle targets remain unmet. The v0.5.0 signed release reached 2,009 ms p95 in its matched-build standalone trial. Earlier signed v0.4.0 trials had lower absolute times, showing that timings vary between sessions and that a cross-session difference is not a controlled version regression or gain. Further reductions need profiling of the renderer's initial bundle and extension-host startup, then narrow changes that retain API registration and feature behavior. Broadly removing AI/MCP contributions now would risk extension services without a demonstrated net memory benefit.
