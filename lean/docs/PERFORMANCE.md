# Performance and version history

Lean VS Code's public comparison uses **unmodified Code-OSS 1.139.1 source at the fork's base revision** (`04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1`). It is a more useful causal baseline than a differently configured Visual Studio Code download. The reference Mac is an Apple M3 Max with 36 GiB of RAM running macOS 27.0.0. These are measured results on that machine, not guarantees for every project or Mac.

| Build | Editable file, median / p95 | Already-open window, median / p95 | Idle app-tree footprint, median | Against Code-OSS in the same run |
| --- | ---: | ---: | ---: | --- |
| [Code-OSS paired with v0.2.0](../performance/v0.2.0-vs-code-oss-1.139.1.json) | 2,010 / 2,151 ms | 403 / 434 ms | 878 MiB | Baseline |
| [Lean v0.2.0](../performance/v0.2.0-vs-code-oss-1.139.1.json) | 1,644 / 1,703 ms | 404 / 436 ms | 743 MiB | 18% less time to an editable file; 15% lower idle footprint |
| [Code-OSS paired with v0.3.0](../performance/v0.3.0-vs-code-oss-1.139.1.json) | 2,002 / 2,052 ms | 393 / 428 ms | 854 MiB | Baseline |
| [Lean v0.3.0 signed release](../performance/v0.3.0-vs-code-oss-1.139.1.json) | 1,640 / 1,714 ms | 380 / 417 ms | 746 MiB | 18% less time to an editable file; 13% lower idle footprint |

The v0.2.0 and v0.3.0 rows preserve separate paired trials against the original Code-OSS baseline, so their percentages use the Code-OSS result **from the same run**. Differences between the two Lean rows alone are not a controlled version-to-version effect. The development candidate's [same-run comparison with v0.2.0](../performance/v0.3.0-candidate-vs-v0.2.0.json) showed under 1% median startup difference for a standalone file. In a generated repository with 10,000 tracked files, the [candidate versus v0.2.0 comparison](../performance/v0.3.0-candidate-git-vs-v0.2.0.json) showed no repository-open startup improvement: 1,662 ms versus 1,652 ms median. Git activation is now demand-driven, but it should not be advertised as a measured file-ready speedup. The [earlier candidate versus Code-OSS trial](../performance/v0.3.0-candidate-vs-code-oss-1.139.1.json) remains available as development evidence; public headline numbers use the signed release trial.

The harness alternates product order over **30 warm-cache launches per product** and 30 file opens in existing windows. Each launch gets isolated user-data, shared-data, and extension directories. Both apps load the same small benchmark control extension, which marks a 100 KiB text file ready after it becomes the active editor and passes a reversible edit probe. The file-open measure starts when the app CLI is invoked with `--reuse-window`. Three memory snapshots follow 30 seconds of idle time. For each app process and child, the harness reads macOS `footprint`'s `phys_footprint` and sums those readings. Shared pages can appear in more than one process's accounting; this is a comparative app-tree measure, not a unique-physical-pages count or the memory used by every possible extension. [Harness instructions](../../scripts/lean-perf/README.md) explain how to repeat it.

The Code-OSS baseline was built from the exact upstream source revision. Its packaging task omitted the Copilot SDK directory, so that directory was copied from the same revision's installed source dependencies into the otherwise built app before ad-hoc signing for the local trial. This repairs a packaging omission without changing the source behavior; it is still a source-built comparison, not a stock Microsoft Visual Studio Code release. The v0.2.0 app was the signed installed release. The v0.3.0 final run used the signed and notarized release bundle extracted from the DMG built from fork commit `13fbbf8e65a1733a0b03ce47111d2f1a00c31b02`.

These runs do **not** establish true cold-cache launch time, peak memory, large-file performance, long-session leak freedom, or universal extension compatibility. The original plan's 1-second file-ready and 250 MiB idle targets remain unmet. Further reductions need profiling of workbench and helper-process costs, then narrowly tested deferral of optional services and extension-host startup. Broadly removing AI/MCP contributions now would risk extension services without a demonstrated net memory benefit.
