# Startup roadmap: editable file in under one second

This is a research-backed **proposal**, not a performance claim or a release commitment. The goal is to open a small file from a stopped process and reach an editor that accepts input at **p95 ≤ 1,000 ms**, while retaining editing, local review, terminal, installed extensions, and restored editors. The existing [benchmark definition](../../scripts/lean-perf/README.md) includes an extension-host edit probe; a faster blank window or first paint does not satisfy this goal.

**v0.4 implementation update:** Profiling changed the first batch. A synchronous remote-service listener lookup was removed from startup, the macOS release build now uses the optimized minified bundle, and the shared utility process begins its existing single-flight startup after the first real window opens. A bundled-extension manifest index and earlier extension scan were prototyped but not retained: their paired GUI trial did not improve the editable-file endpoint. The numbered ideas below remain the original research roadmap and are not a list of changes shipped in v0.4. See [performance history](PERFORMANCE.md) for release measurements when available.

**v0.5 development update:** Starting local extension initialization as soon as the workbench reaches Ready, without an extra idle callback, passed the editing/search/terminal/Git/webview GUI smoke checks. A 30-pair unsigned-candidate trial against signed v0.4.0 showed a directional 1,403 versus 1,432 ms median, but different signing/provenance means this is not release evidence. Moving initialization still earlier, into the extension service constructor, failed the editable-file warm-up after 120 seconds and was reverted. A macOS-only renderer specialization changed the minified bundle by only 83 bytes and was also reverted. The exported esbuild graph showed only about 240 KiB of exclusive optional chat-editor code behind two easy import edges; a whole-chat lazy import would remove more code but disrupts synchronous service and restored-editor registration. A separate five-pair persistent-profile diagnostic against Code-OSS remained above one second, so the target has not been met. These are internal experiments; public speed claims compare signed releases with original same-revision Code-OSS only.

**Rejected extension-host prewarm:** A gated macOS prototype forked the local extension host when the renderer requested its shell environment and attached the message port after final launch options were known. Normal local-window launches claimed the prepared host, but the observed lead before the renderer needed it was only 40, 26, and 7 ms across three exploratory launches, including an earlier shell-environment warmup. The prototype added process lifecycle, environment-matching, and fallback complexity for too little available overlap, so it was removed before release. These launches were diagnostic, not a paired Code-OSS performance claim.

The signed v0.3.0 Apple M3 Max reference build measured **1,640 ms median / 1,714 ms p95** across 30 warm-cache isolated-profile launches; matched Code-OSS measured **2,002 / 2,052 ms**. Reaching the goal from that release requires at least **714 ms (42%) off its p95**. The patch release v0.3.2 has no new full benchmark. See [measured history](PERFORMANCE.md). The earlier demand-driven Git change did not materially improve file-ready startup, so it is not counted again.

## First: measure the critical path

Before changing startup, capture main, renderer, extension-host, and shared-process spans on a dedicated Apple Silicon test session. Use VS Code's existing startup performance marks, contribution warnings, service-instantiation trace, and `--prof-startup`; add targeted marks only where the trace lacks a boundary. Separate process start, Electron/native startup, window creation, renderer module evaluation, contribution construction, file restoration, built-in extension scan, extension-host readiness, and edit-probe completion. Record a separate first-visible-file mark so shifting work after paint cannot masquerade as file-ready improvement. The [VS Code performance tools](https://github.com/microsoft/vscode/wiki/%5BDEV%5D-Perf-Tools-for-VS-Code-Development/a534a1e415b67d4b9fe5a0c936e787c318734484) and [Electron performance guide](https://www.electronjs.org/docs/latest/tutorial/performance) both recommend profiling before deferring work.

Run GUI profiles and paired benchmarks when the physical Mac desktop is available for testing; editor windows can take focus. Keep profiling runs separate from headline timing because profiling adds overhead. Do not call VM or headless timing equivalent to the signed physical-Mac result.

## Proposed v0.4.0: three changes in priority order

1. **Keep feature registration early; move optional service work out of editor restore.** Profile workbench contributions, then preserve synchronous command, serializer, content-provider, and extension-point registration while making expensive optional backing services initialize on first use. Start with MCP management/context rendering and notebook providers if traces show they execute before the file is ready. A contribution can require early registration yet still defer its constructor's I/O or graph creation. Relevant paths: [`workbench.ts`](../../src/vs/workbench/browser/workbench.ts), [`mcp.contribution.ts`](../../src/vs/workbench/contrib/mcp/browser/mcp.contribution.ts), and [`notebook.contribution.ts`](../../src/vs/workbench/contrib/notebook/browser/notebook.contribution.ts). Gate: same file-ready probe plus commands invoked immediately at launch, restored notebooks/custom editors, early events, and terminal startup. VS Code has [documented slow early contributions](https://github.com/microsoft/vscode/issues/159675); profile this fork before choosing any one to defer.
2. **Prototype a generated index for bundled extensions.** The release has a fixed, curated built-in extension set. Measure the system-extension scan; if it is on the critical path, generate an immutable manifest index at packaging time and read it as one validated input. Keep normal scans and precedence for user, workspace, development, remote, and overridden extensions; fall back to the scanner if the index or locale is incompatible. Relevant paths: [`cachedExtensionScanner.ts`](../../src/vs/workbench/services/extensions/electron-browser/cachedExtensionScanner.ts), [`extensionsScannerService.ts`](../../src/vs/platform/extensionManagement/common/extensionsScannerService.ts), and [`gulpfile.vscode.ts`](../../build/gulpfile.vscode.ts). Gate: identical extension descriptions/activation order, localization, install/uninstall/override behavior, and cold-profile correctness. Drop this candidate if scanning is already hidden by another task or its measured saving is negligible.
3. **Overlap extension preparation with window setup where dependencies allow.** The local extension host currently starts only after the workbench reaches Ready, then schedules initialization with a 50 ms idle limit in [`nativeExtensionService.ts`](../../src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts). Measure whether safe scan preparation or process bootstrap can begin sooner without competing with the renderer for CPU or changing activation order. This is *not* a blanket delay of the host: some restored editors need it, and the benchmark's edit probe runs inside it. Gate: CLI/Finder file opens, restored editors, startup activation, shell environment, trust prompts, and extension-host crash/restart behavior.

Implement and measure these separately. Keep a change only if it improves the existing file-ready endpoint (or a clearly identified memory endpoint) without a feature regression. The nominal 50 ms idle limit alone cannot explain the full 714 ms p95 gap.

## Proposed v0.5.0: next three, after v0.4 measurements

1. **Split optional workbench implementations from the initial renderer bundle.** Keep small registrations/API entry points in the startup graph, but load optional chat/MCP, notebook, debug, and browser-view implementations when used. Inspect the emitted bundle graph first; a dynamic import that still lands in the initial chunk saves nothing. Relevant paths: [`workbench.common.main.ts`](../../src/vs/workbench/workbench.common.main.ts), [`workbench.desktop.main.ts`](../../src/vs/workbench/workbench.desktop.main.ts), and [`bundle.ts`](../../build/next/bundle.ts). Gate: smaller initial evaluation and memory with no missing commands, assets, CSS, translations, or singleton state; measure first-use latency too.
2. **Instantiate optional extension API/RPC actors on demand.** After the renderer graph is smaller, profile extension-host API construction in [`extHost.api.impl.ts`](../../src/vs/workbench/api/common/extHost.api.impl.ts). Retain synchronous public API shapes and core document/editor/command actors; defer only optional actors that can preserve event and RPC semantics. Gate: an extension compatibility matrix covering editing, SCM, terminal/tasks/debug, notebooks, webviews/custom editors, and startup activation. This is high risk and should be abandoned if it breaks extension contracts or saves little.
3. **Defer optional shared-process channel implementations only if traced on the file-ready path.** Keep channel names and IPC availability; construct optional services on first request. Relevant paths: [`sharedProcessMain.ts`](../../src/vs/code/electron-utility/sharedProcess/sharedProcessMain.ts) and [`sharedProcessService.ts`](../../src/vs/workbench/services/sharedProcess/electron-browser/sharedProcessService.ts). Gate: Open VSX, profiles, multiple windows, cancellation, and shutdown. The renderer already delays some shared-process connection work, so this may deliver **zero** file-ready benefit; replace it with the next measured bottleneck if so.

## Apple Silicon and Electron experiments

- **Native architecture is already correct.** The current macOS executable is `arm64`, so removing Rosetta is not an available gain. Use Apple Instruments/App Launch and dyld traces to measure native load, code-signing validation, page faults, and framework initializers before changing packaging. Keep signed and notarized release builds as the measured product. [Apple's launch-time guidance](https://developer.apple.com/documentation/xcode/reducing-your-app-s-launch-time) provides the platform profiling path.
- **Account for Electron 43 first.** This fork targets Electron 43.6.0. Electron 43 reports an embedded Node startup snapshot, compiled bytecode for framework/preload code, pushed renderer startup data, macOS ThinLTO, and V8 built-in PGO. Verify which of these are present in the pinned distribution rather than budgeting their benefits again. A custom browser-process V8 snapshot can forfeit part of the embedded Node snapshot gain, so test it only as a controlled experiment. [Electron 43 notes](https://www.electronjs.org/blog/electron-43-0); [snapshot fuse caveat](https://www.electronjs.org/docs/latest/tutorial/fuses#loadbrowserprocessspecificv8snapshot).
- **Test resource layout, not just package size.** The current app already packs Node dependencies in `node_modules.asar`; the workbench `out/` tree is loose. If file-open traces show filesystem metadata/read costs, A/B test packing or precompiling the hot workbench resources, including path, source-map, native-module, extension, signing, and update checks. ASAR has [read-only, binary execution, and unpacking constraints](https://www.electronjs.org/docs/latest/tutorial/asar-archives), so this is not a presumed win.
- **Do not substitute a resident background app for process-startup speed.** Prewarming may improve a second open, but it changes the memory/energy cost and does not satisfy the stopped-process measurement. Disabling GPU acceleration, sandboxing, signing, or notarization has no demonstrated benefit here and can reduce correctness or safety.

## Release decision and public claims

For each proposed change: make a single-variable candidate, preserve feature/extension behavior, profile the affected span, then run at least 30 alternating signed-release launches against the same-upstream Code-OSS build on the same physical Apple Silicon Mac. Report median, p95, raw samples, idle app-tree memory, and first-use cost of any deferred feature. Keep direct Lean-version trials for internal regression diagnosis. Full public comparisons belong to minor releases; patch releases get targeted performance checks only when warranted. Update [performance history](PERFORMANCE.md), the README, website, and changelog with **measured Code-OSS baseline gains** and exact build labels. Do not advertise a sub-second result until the editable-file p95 actually meets it.
