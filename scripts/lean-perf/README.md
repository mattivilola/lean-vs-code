# Lean VS Code performance harness

This harness compares an installed Lean VS Code app bundle with an unmodified Code-OSS app bundle on macOS Apple Silicon. It records startup-to-editable-file samples, file-open samples sent to an already-running window, and idle memory for the whole app process tree. It does not install or change extensions or settings in the real user profile. The primary v0.6 target is **established profile, CLI and Finder launches, first UI edit p95 ≤ 1.0 s**. Extension-backed editability is a secondary endpoint.

For public release comparisons, run the full paired harness when the upstream base or architecture changes materially, a substantial performance change is made, or a new public speed or memory claim is needed. Routine patch and minor releases can use focused regression checks and keep the last full result labeled with the exact measured version. Retain failures and raw observations for every published claim. This GUI harness opens editor windows and can take desktop focus, so run it only when the desktop is available for testing.

## Run

Build or install both app bundles from the same Code-OSS base revision, then run from the repository root:

```sh
node scripts/lean-perf/benchmark.mjs \
  --lean-app "/Applications/Lean VS Code.app" \
  --oss-app "/Applications/Code - OSS.app" \
  --base-revision 04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1
```

The default is 30 timed startup and 30 existing-window file-open samples per product, one startup warm-up per product, a 5-second existing-window settle period, 3 memory snapshots after 30 seconds of idle time, and an output directory under `scripts/lean-perf/results/`. Pass `--samples`, `--memory-samples`, `--memory-idle-ms`, or `--output-root` to adjust the run. Every run gets a new report directory and a short, isolated profile directory under `/private/tmp/lean-perf-*`; both are retained for inspection. No existing profile is opened or removed.

To keep GUI tests in a compact bottom-left window on the current 1512 × 982-point Mac display, add `--window-bounds 16,546,560,360`. The harness writes the same requested bounds into each app's isolated profile *before* a launch, so placement work is outside the timed startup interval; the manifest records the coordinates. Width must be at least 400 points and height at least 270 points. Recalculate the top-left `y` coordinate if the display or Dock changes. This keeps the window small but macOS may still briefly focus it; do not run GUI tests during work that cannot tolerate a focus change. Use identical bounds for both apps in every paired comparison, and do not compare results from different window sizes as though geometry had no effect.

To investigate a process-role memory outlier, run independent stopped-app launches with one short-idle snapshot from each fresh isolated profile:

```sh
caffeinate -dimsu node scripts/lean-perf/benchmark.mjs \
  --lean-app "/Applications/Lean VS Code.app" \
  --oss-app "/path/to/Code - OSS.app" \
  --base-revision 04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1 \
  --memory-only --memory-launches 9 --memory-samples 1 --memory-idle-ms 30000
```

The apps alternate first position by pair. The run still makes one unmeasured startup warm-up per app, but skips timed startup and existing-window trials. Inspect `summary.json` and every raw `wholeProcessTreeMemory` sample, especially the `gpu` role count and variance. A missing GPU process is not a zero-byte GPU sample. Record display and window conditions beside the report. Only complete, matched pairs support a comparison; this measures short-idle summed process footprints, not peak or long-session memory. To publish a path- and PID-free copy of a complete run, use `node scripts/lean-perf/export-public.mjs <run-directory> <output.json>`.

For a focused editable-file startup regression, pass `--startup-only --samples 30` with two otherwise matched apps. It keeps the same control-extension VSIX, warm-up, and alternating product order, but skips the existing-window and idle-memory phases. Use `--reuse-startup-profile` to test repeat launches with each app's own established profile. A Lean-versus-older-Lean trial diagnoses a candidate; public speed percentages still require original same-revision Code-OSS and a tested release build. Do not merge a fresh-profile result with an established-profile result.

For internal regression diagnosis, a candidate may be compared against an earlier Lean VS Code release by passing that app as `--oss-app` and setting `--oss-label 'Lean VS Code v0.2.0'`. Do not use that trial as a public speed claim: published performance comparisons use original same-revision Code-OSS. The raw sample key remains `code-oss` for compatibility with the standard comparison parser; use the manifest's app paths and labels when interpreting such a run.

Pass `--git-workspace` for a separate repository-opening benchmark. It creates a task-owned Git fixture under that run's report directory and opens the fixture file with the folder; the default run is a standalone file. Keep these results separate because bundled Git activation is relevant only to the repository case.

First validate bundle paths and inspect the plan without launching either app:

```sh
node scripts/lean-perf/benchmark.mjs \
  --lean-app "/Applications/Lean VS Code.app" \
  --oss-app "/Applications/Code - OSS.app" \
  --base-revision 04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1 \
  --dry-run
```

Run the built-in fixture smoke check with `node scripts/lean-perf/smoke.mjs`. It uses fake app metadata and never launches an editor.

For a real GUI feature check against a built or installed app, run `node scripts/lean-perf/functional-smoke.mjs "/path/to/Lean VS Code.app"`. This launches an isolated profile and temporary Git workspace, then verifies editing and saving, 10 returned text-search matches among 400 source files, an integrated terminal command, a local Git diff, and extension-host webview creation. The aggregate `all` scenario enables the same proposed text-search API for its temporary control extension as the dedicated search scenario. It writes a per-check JSON result and app log under `.build/lean-artifacts/functional-smoke/`. It does not use the normal user profile. The window can take focus, so run it when the desktop is free.

For a paired first-use workflow diagnostic, run `node scripts/lean-perf/workflow-benchmark.mjs --lean-app "/Applications/Lean VS Code.app" --oss-app "/path/to/Code - OSS.app" --base-revision 04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1 --scenario gitReview --samples 30 --lean-label "signed Lean v0.4.0, minified" --oss-label "original Code-OSS 1.139.1, minified"`. Supported scenarios also include `integratedTerminal`, `workspaceSearch`, `workspaceTextSearch`, `editableFileAndSave`, and `extensionWebview`. Each trial launches a fresh isolated one-file Git workspace, except `workspaceTextSearch`, which uses 400 source files and verifies 10 returned text matches via the same proposed search API enabled in both apps. The older `workspaceSearch` smoke only opens the Search UI and is **not** a completed-result timing. The report separates **action time inside the temporary extension after `onStartupFinished`** from **process spawn to completed workflow**. The latter includes app startup, but is not a key-to-paint measurement. `gitReview` waits for the requested file to become the active editor, runs the Source Control command, waits for the bundled Git extension to find the repository, and reads its diff; `integratedTerminal` waits for a marker written by an actual shell command. `editableFileAndSave` marks completion once saved bytes are verified on disk, before the fixture is restored. Targeted checks poll at 20 ms, which still limits precision for very short timings. Alternate app order, retain failures, and compare against original same-revision Code-OSS. Do not turn a short exploratory run into a public claim; use at least 30 pairs and disclose build provenance. See the [developer workflow benchmark matrix](../../lean/docs/BENCHMARK_MATRIX.md) for proposed completed-task measurements and claim gates.

Keep the Mac awake for the entire paired run, for example by prefixing the command with `caffeinate -dimsu`. A macOS idle-sleep event invalidated an earlier terminal trial: its timeout samples remain in that raw report, but its percentiles are not suitable for a public claim. Stop the run and repeat it from scratch if the machine sleeps, thermally throttles, or a trial times out.

For a diagnostic renderer startup trace, run `node scripts/lean-perf/trace-startup.mjs "/path/to/Lean VS Code.app" "/path/to/file.txt" "/path/to/trace.json"`. Add `--launch-mode direct|cli|finder`, `--reuse-profile`, or `--chromium-trace /path/to/chromium.json` before the positional arguments. Profile reuse performs an untraced warm-up, waits for its control extension, and quits through the editor before tracing the second launch; it fails rather than calling a signal-killed run an established cache. Chromium tracing uses `--trace-startup`, `--trace-startup-file`, and a 10-second duration because VS Code's `--trace` starts `contentTracing` but has no file-output argument for this script. The JSON includes the app product commit, launch mode, profile condition, and `controlExtensionInstall: 'vsix'`. This launches an isolated profile, records Monaco performance marks through the Chrome DevTools Protocol, and writes the Startup Performance report beside the JSON trace as `trace.json.perf.md`. Its temporary control extension is installed as a normal user extension before launch, keeping the extension host out of development mode so code caches behave as in daily use. It requests the report during the traced launch, which can change the restored editor; use the paired benchmark above for release timing claims. Trace artifacts may include local file paths, so review them before publishing.

For a separate **requested-text visibility diagnostic**, run `caffeinate -dimsu node scripts/lean-perf/visible-file-benchmark.mjs --lean-app "/Applications/Lean VS Code.app" --oss-app "/path/to/Code - OSS.app" --base-revision 04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1 --samples 30`. Both apps use a local remote-debugging port and an isolated short macOS profile. After one warm-up each, the script alternates launches and polls for a unique requested text marker in a nonzero-size Monaco editor DOM element. Its result is a DOM visibility proxy; it does not measure physical display paint, focus, or editability. Keep it separate from the extension-backed editable-file benchmark and retain failed or slow samples.

Add `--input-probe` to the same command for a separate **first UI edit diagnostic**. Once the requested text is visible, the harness focuses Monaco's native EditContext (or textarea input on builds that use one), sends unique synthetic text through the Chrome DevTools Protocol, and waits until it appears in the visible editor lines. The fixture remains unsaved. This tests UI response to synthetic input, not a physical keypress, saved edit, or extension-host API readiness. Export a complete run with `node scripts/lean-perf/export-public.mjs <run-directory> <output.json>`; the exporter refuses missing or failed observations and removes local app-log paths.

Use `--launch-mode cli` to start via each bundle's `Contents/Resources/app/bin/code` script (with `bin/<applicationName>` as a fallback for bundles that ship it), or `--launch-mode finder` to start through LaunchServices; `direct` remains the default. Add `--reuse-profile` for daily-use measurements: each app receives one isolated profile, the warm-up seeds it, and all timed launches reuse it after the prior app process stops. Before the warm-up, the harness writes `{ "window.restoreWindows": "none" }` to that temporary profile's `User/settings.json` so restored windows do not accumulate. The manifest and every raw sample record launch mode and profile condition. Profiles remain under `/private/tmp/lean-visible-*` and never use the real profile. Finder does not pass the caller's environment to the app; this DOM/CDP benchmark uses arguments and files, so Finder mode works here.

Add both `--input-probe --second-window` to measure **second-project-window first UI edit**. Each trial starts an isolated app profile, waits until the first window shows its own fixture file, then launches another window in that same app instance with a different fixture using the selected launch mode. Timing starts when the second-window launcher is spawned and ends when synthetic input appears in that second editor's visible lines. The report also retains first-window readiness for context. With the default fresh-profile mode, each pair gets a new profile; established-profile mode reuses the app's profile while stopping the app between trials. This measures second-window response with an already-running app, separate from stopped-process startup, and does not claim physical paint or extension-backed editability.

For a separate **installed app-bundle size** comparison, run `node scripts/lean-perf/bundle-size.mjs --lean-app "/Applications/Lean VS Code.app" --oss-app "/path/to/Code - OSS.app" --base-revision 04c0d99f4fb0d8afe6ce4f0c58e31e183ac3e4b1 --lean-dmg "/path/to/Lean-VS-Code-0.4.0-macos-arm64.dmg" --output "lean/performance/bundle-size.json"`. It uses macOS `du -A -sk` for apparent bundle size and `du -sk` for allocated disk blocks, and records extension-directory and source-map counts. A DMG is an **absolute** byte size unless a matched Code-OSS DMG is also supplied. Compare equivalent release/source build modes and record package provenance. Bundle size is neither runtime memory nor compressed download size.

For the [v0.4.0 independent-launch memory comparison](../../lean/performance/v0.4.0-independent-memory-vs-code-oss-1.139.1-minified.json), the existing paired benchmark was run once per fresh profile and app pair with `--samples 1 --memory-samples 1 --memory-idle-ms 30000`. A controller alternated `--lean-app`/`--oss-app` roles between pairs, then retained the readings for the actual product; it kept `caffeinate -dimsu` active and checked the macOS power log for sleep across the included series. The published report contains nine complete pairs, order, per-process-tree totals, and process counts. One pilot pair separated by system sleep was excluded from the reported series. This method supports only short-idle app-tree comparisons; peak and extended developer-session memory remain to be measured.

## Method

The harness requires `arm64` macOS. Each startup trial gets unique user-data and shared-data directories. Before timing, it installs the same small control-extension VSIX into that trial's isolated extensions directory using the app's CLI. Established profiles install it once before warm-up. The extension host therefore starts as a normal, non-development host, allowing Node code caches to behave as in daily use. The control extension declares untrusted-workspace support so it activates in a fresh profile's Restricted Mode without disabling workspace trust. It performs one raw-only startup warm-up per product before the measured repetitions. The 100 KiB text fixture is read before timing to warm filesystem contents. Timed startup trials use a fresh profile by default and alternate product order each repetition. Existing-window trials keep one isolated window per product, settle for five seconds, then alternate which product opens a new fixture file first. The manifest records `controlExtensionInstall: 'vsix'`. `benchmark.mjs --launch-mode cli` uses the bundle CLI. Finder mode is rejected here because LaunchServices does not pass the control extension's `LEAN_PERF_CONTROL_DIR` and `LEAN_PERF_STARTUP_FILE` environment variables to the app.

Readiness is recorded after VS Code reports the requested file as the active text editor and accepts a reversible `TextEditor.edit` insertion/removal probe. This checks that the extension API can edit the document and restores the fixture contents. The startup number runs from process spawn until the harness sees that readiness marker. The existing-window number runs from spawning the app executable with `--reuse-window <file>` until the running app reports the matching editor as ready. These are app-level file-ready timings; the editability probe is not a hardware key-to-paint measurement.

Memory samples wait for an editable fixture window, idle for the configured interval, then enumerate descendants of the app's main PID with `ps`. For every PID, the harness runs macOS `/usr/bin/footprint` and reads `phys_footprint`; it sums those per-process values for the reported app-tree total. Each raw process includes PID, role, physical footprint, and RSS, with per-sample role totals and a `byRole` summary in `summary.json`. Roles include `main`, `renderer`, `gpu`, `network`, `extensionHost`, `sharedProcess`, `ptyHost`, `fileWatcher`, and `utility:<sub-type>`; unknown utilities are labelled `utility:unknown` and other unmatched processes `other`. RSS, derived from `ps`, is included only as a separate diagnostic. The metric is Apple's process physical-footprint accounting, not resident-set size; see Apple's [`ri_phys_footprint` documentation](https://developer.apple.com/documentation/kernel/rusage_info_v1/1577496-ri_phys_footprint). A complete total is emitted only when every observed process has a readable footprint; permission or process-exit errors remain in the raw sample as unavailable values. Access to other processes can be restricted by macOS privacy settings, so rerun from a terminal with appropriate process-inspection access if the capture is incomplete.

The process tree is sampled over a short interval rather than atomically. `footprint` reports per-process accounting; summing it does not deduplicate shared pages between processes. Treat the total as the sum of macOS billed footprints for the observed tree, and do not compare it with Linux PSS or Windows private bytes. Child processes that detach or are reparented outside the launched process tree may not be included.

The report records both app `product.json` versions/commits and the operator-supplied `--base-revision`. The supplied revision is a comparison label, not a cryptographic proof that both binaries came from that source revision. Verify build provenance independently before drawing causal conclusions. The invoking environment is inherited by the apps for normal launch behavior but is never written to the report.

## Output

Each unique result directory contains:

- `manifest.json`: machine, product metadata, fixture size, flags, settings, and supplied comparison revision.
- `samples.jsonl`: raw timing and memory observations, including startup warm-ups, written as the run proceeds. Warm-ups are excluded from percentile summaries.
- `summary.json`: per-product p50/p95/min/max and sample counts. Percentiles use nearest rank (`sorted[ceil(p*n)-1]`); failed samples stay visible in the raw file and do not enter the percentile calculation.
- `/private/tmp/lean-perf-*`: isolated per-run profiles, kept outside the report directory so Electron's Unix socket paths fit macOS's limit. The relative profile paths in raw samples point to them.
- `trials/`, `fixtures/`, `harness-extension/`, and `harness-extension.vsix`: harness-owned run artifacts for inspection. Each trial's `control/app.log` captures launch errors.

The default sample count follows the repository performance plan. Reduce it for a smoke run, then use at least 30 repetitions for reported warm-cache timing results. This harness does not reset the filesystem cache or claim reboot-cold startup.

For a separate diagnostic of repeated launches with each app's own persistent profile, pass `--reuse-startup-profile`. The warm-up seeds the profile, and later launches reuse it while still starting a stopped app process. The harness writes `{ "window.restoreWindows": "none" }` in that temporary profile before warm-up to prevent restored windows from accumulating. The manifest records this override and the established profile condition. This can expose V8 code-cache and persisted-state effects; keep its results separate from the default fresh-profile series and compare Lean only with original Code-OSS run in the same mode. Public claims still require at least 30 alternating pairs, original same-revision Code-OSS, and retained failures.
